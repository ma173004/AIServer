# 總結-20261126-目前實行架構與問題

> 用途：給主人做一次「目前實行架構」大總結的底稿；也是下一輪「反架構本身、可持續發展性」證反的輸入。
> 只描述現在真的在跑的，不把目標設計混進來。已實作／未實作會分開標。

## 0. 一句話

映月目前是「單一 FastAPI 入口 + 多段生成 + 多個 JSONL 狀態檔 + 多個側迴路」的本地優先伴侶系統。  
它已經能跑完整回合、有記憶、有情緒、有獨處思考；但**控制面、狀態一致性、可回滾性、輸出單一性**仍是架構債。

## 1. 入口與回合

### 真的在跑
- `agents/dshmid.py`：FastAPI `127.0.0.1:11435`，OpenAI 相容 `/v1/chat/completions`，SSE 串流。
- 入口來源：DSH Web GUI、Discord bot（owner／guest）、probe、scheduler／task_runner 觸發。
- audience 分線：owner／guest；guest 走 `agents/guest.py`，有 allowlist、關係卡、guest bank。
- 多入：MIMO 700ms 批次窗（`_MI_STATE`）；P06 Phase 1A/1B 已加每訊息 ledger／owner-scoped finish／replied 終態／coverage shadow。
- 回合內有 audience 鎖；背景反思、mind_loop、collector 各自跑 thread／進程。

### 關鍵事實
- 一請求一 pipeline 一回覆；批次合併時一輪可只回一個 bubble。
- `turn_done` 是終點標記，`elapsed_s` 是整輪總耗時，不是工作階段。
- `AGENT_FREEZE=1` 時，writing／learning／generic／code／work 一律 redirect 到 task；五個舊 agent 不進生產。

## 2. 回合管線

1. 入口收訊息 → pending／批次 → `_mi_begin`／`_mi_collect`／`_mi_finish`。
2. `agents/diaoyongai.py::qwen_decompose`：intent、subtasks、skills、need_search、confidence。
3. 記憶召回：`agents/memory.py::recall_memories`（Hindsight）。
4. `agents/executor.py`：按子任務 agent 執行（chat／task／research；凍結者 redirect task）。
5. `q3_polish`／fusion：把工具結果／多子任務結果寫成回覆草稿。
6. 輸出清理：`agents/replyfmt.py`（標籤、舞台指示、偽工具、尾端動作）＋`agents/zhtw.py`（繁中）。
7. 送出：dshmid 回覆；Discord bot／outbox／followup／thought_loop say／notify 各自送。
8. 回合後：session log、trace、turn ledger、after_turn、dialogue reflection、self_observe、notify。

### 已知摩擦
- 輸出沒有單一出口；主回覆、followup、outbox、thought_loop say、task 通知各自送。
- `q3_polish` 曾是模型改寫層，效果不好被撤；目前各段靠檔案／queue 接力，沒有共享 turn state。
- 2026-11-26 起凍結 agent 廣度；文字類請求目前仍會落到 task 路徑（正文可直出，但語氣像通用助手）。

- 多數是 ad-hoc JSONL，少數有 flock；沒有統一 schema migration、交易、回滾。

## 5. 側迴路

- `thought_loop`：idle 每 30 分鐘／after_turn 回合後；產 thought／want／say／line／act。
- `dialogue_thread`：每回合反思、對話線狀態、沉澱。
- `mind_loop`：每 180 秒，dry_run 不發消息，但 `feed_thought` 會進 dialogue_thread【我正在想】；目前資訊多樣性低。
- `self_questions`：問題清單；`outbox`／`followup`：主動訊息通道。
- `consolidate_worker`：夜間記憶固化 shadow；`collector_daemon`：採集＋事件。
- 這些迴路都會把材料寫回主 context，形成「側迴路→主 context→再生成」的閉環。

## 6. 控制面與可觀測性

- 健康：`/health`（dshmid）；`log_viewer` 頁：`/coverage`、`/shadow`、`/turn`、`/timing`、`/faults`、`/reflux` 等。
- 測試：`scripts/run_all_tests.sh`，179 組；多為 fixture／單元，E2E 覆蓋不足。
- 控制：目前靠環境變數＋重啟（如 `AGENT_FREEZE`、`THOUGHT_LAST_REPLY`、`MASTER_WRITES_FROZEN`）。沒有統一控制 API、沒有操作審計、沒有權限分層。
- 主人要寫前端做總體控制：目前可直接接的只有 health／頁面／chat API；其餘都是檔案或 env，需要先做控制面，不然前端只是另一個看板。

## 7. 目前主要問題（與問題清單對應）

### 高把握、已反覆出現
- P01 after_turn 強制生成：每輪必填 say／line，沒有「這輪不需要說」的出口。
- P02 無依據數字／清單：7 欄位、47 分鐘、47 秒等，沒有 evidence gate。
- P03 看不到自己已送出的話：idle 只有 thoughts／continuity，沒有 sent history。
- P04 會話不連續：session_id 每回合新 uuid；沒有穩定 conversation id。
- P06 訊息所有權：Phase 1A/1B 已加 ledger／終態，但 carried／re-queue 未做；queued 仍可能只被清不回。
- P07 外部事件沒有消費決策：events 有資料，只有 mind_loop 讀，沒有 info_decision。
- P12 主題級重複：表面字不同，主題繞回。
- P14 自發專案執著：continuity／workbench／questions 形成項目槽位。
- P15／P33 人稱／自我指涉：自己的 proactive／thoughts 回流，自己的話說成主人說的。
- P28 after_turn 語義歸因錯：把批評記成語病、把責任推回主人。
- P29 continuity 合併與欄位不同步：舊 raw 配新 topic，無關項目併成一條。
- P30 輸出證據：無依據 claim 仍可送出；P31 問句尾巴與責任外推。
- P32 測試資料污染生產狀態：年糕、貓、舊 last_reply 等。
- P06 後新增：P06 Phase 1A/1B 只解生命週期，還沒解「有回但沒回答」的 coverage。

### 已修／已凍結
- `</inner_monologue>` dangling 泄漏：2026-11-26 已修（replyfmt 共用出口）。
- 五個 agent 凍結（writing／learning／generic／code／work），不恢復。

## 8. 給「反架構本身」的證反問題

1. 單一 dshmid 進程＋in-memory audience 鎖＋thread 池，是否是可持續的控制面？前端要做總體控制時，是否必須先拆 control plane／turn engine？
2. 多個 JSONL 狀態檔沒有交易、schema、migration；在資料量／功能增長下，什麼時候會先壞？要先補哪一個？
3. 六個側迴路都能寫回主 context；哪些應該保留、哪些應該改成 pull-only、哪些應該直接刪？
4. 輸出五條以上、沒有單一出口；如果只做一個「輸出閘」，應該放在哪裡、用什麼契約，才不會變成第二個 q3？
5. 上下文沒有 manifest／provenance；如果只做一個最小版本，應該是「每塊來源＋時間＋可信度」，還是「只做四類高風險塊 deterministic 過濾」？
6. 測試 179 組但 E2E 不足；最低可接受的 production gate 是什麼？
7. 如果要撐 6–12 個月，現在最該刪的是什麼？最該保的是什麼？
8. 主人要寫前端：最小控制面 API（讀狀態、改 flag、看 approvals、kill switch、看 log）應該包含什麼？哪些操作必須二次確認？

## 9. 可持續發展性（待紅隊與主人一起定）

- 功能廣度已凍結；下一步不是加功能，是**上下文、人稱、控制面、可觀測性**。
- 前端不是先寫 UI，是先定 control plane；否則前端只能看舊頁面。
- 任何新增能力都要先問：它會唔會把更多材料寫回主 context？會唔會多一條輸出通道？能否 replay／回滾？
