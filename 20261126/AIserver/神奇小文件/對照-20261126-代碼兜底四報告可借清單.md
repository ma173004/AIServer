# 對照：代碼兜底四報告可借清單（2026-11-26）

> 範圍：`07-代碼層兜底橫向對照`、`04-AstrBot-代碼層優化`、`05-MaiBot-代碼層優化`、`06-Pallas-代碼層優化`。
> 原則：只列「能落到映月現有代碼、零或低模型呼叫、可回滾」的項目；不把別人的架構整套搬進來。

## 0. 先修正一句話

「比 MaiBot 完整不少」不成立。準確說法是：

- **伴侶功能廣度**：映月有本地世界、T6、睡眠、thought_loop、continuity、Hindsight、四線分流；這部分比 MaiBot 貼身。
- **工程完成度**：MaiBot/Pallas/AstrBot 在代碼兜底、訊息生命週期、提示詞資產化、schema/遷移、輸出確定性加工上，成熟度明顯高於我們。
- **別人有 1M context/API**：這是真實優勢，不能拿「他們 prompt 差」自我安慰；但代碼兜底與 context 長度無關，現在就能補。

## 1. 07 的共同結論

三家 prompt 臃腫不是因為寫得多，而是**每條要求都沒被分配執行者**；預設執行者只剩模型自覺，所以只能反覆強調。可借四原則：

1. 可量化判斷搬出模型（門禁、引用、回不回、長度、字符集）；
2. 只做刪減，不改寫（刪不需要模型，改寫需要）；
3. 寧可靜默，不可偽成功（發送失敗不能記 delivered）；
4. 用能力剝奪代替指令懇求（拔工具、從 schema pop）。

七級可判定性：L0 計數/長度、L1 字符集、L2 精確短語、L3 結構模式、L4 形狀/契約 → 應由代碼；L5 語義等價（LLM 加工後與原文重建比對）→ 可做保真校驗；L6 語義類別（涉政/越獄/身份漂移）→ 只能模型。
三家合計裸奔 29 條、其中約 21 條可用「發送前確定性加工＋白名單」覆蓋。

## 2. 可借 Top 6（按我們現況排序）

### A. 發送前確定性加工＋逐字符白名單（最高優先，成本最低）

- 來源：Pallas `structured_reply.py:165-219`（`validate_reply_chars`）、`output_filter.py:211-274`；07 的「一天可覆蓋 21/29」。
- 我們現況：`agents/replyfmt.py` 已有剝標籤、剝偽工具、剝舞台指示、剝句尾動作；但**沒有 markdown/URL/字符白名單/長度硬上限/前後綴清理/是否回答當前問題的檢查**。
- 落點：`agents/replyfmt.py` 新增 `final_output_clean()`，在 `dshmid` 最終回覆出口呼叫；只刪不修，失敗回空並記 faults。
- 可抄細節：`_BAD_TOKEN_CHARS`、`_ALLOWED_ASCII_PUNCT`、`_MAX_REPLY_CHARS`、逐字符 reason、空段丟棄。
- 不抄：Pallas 的完整 11 步 shape 系統（我們的段落模型不同）；AstrBot 的「盡力修復」（隱藏錯誤）。

### B. 提示詞要求 → 執行者映射（L0–L6）

- 來源：07 核心產出。
- 我們現況：prompt 裡「不要/必須/只」很多，但沒有表說明哪條由代碼兜、哪條只靠模型自覺。
- 落點：新 `docs/提示詞要求-執行者映射.md`，逐條列：要求原文、來源檔、可判定級別（L0–L6）、目前執行者（代碼函數／模型自覺）、若裸奔則標紅。
- 先做 owner chat 契約＋人格＋thought_loop 三處；不一次全庫。
- 價值：以後加規則前先問「誰執行」，避免再靠堆 prompt。

### C. Turn budget＋優先級容量

- 來源：Pallas `turn_budget.py:49-55`（60s 共享 deadline、最多 6 次 HTTP）、`execution_budget.py:44-47`（priority capacity）。
- 我們現況：單 GPU、14B、一輪 60–100s；缺少「整輪 deadline」與「聊天優先於主動訊息」的容量控制；idle/研究任務可能與主人對話搶 GPU。
- 落點：`agents/dshmid.py` 回合入口記 `turn_deadline`；`agents/diaoyongai.py` 的 `call_ollama` 讀 deadline；超時走既有 fallback，不新增無限重試。優先級先做最小：owner chat > proactive/idle；低優先級在忙碌時直接 skip，不排隊。
- 不抄：Pallas 的三層信號量＋Redis 協調（我們單進程，過重）。

### D. 字數／context budget：先丟最老，保 system，至少留 64 字

- 來源：Pallas `budget.py:15-36`。
- 我們現況：system 有 2000 硬上限，但 user context 各段沒有統一字符預算；工作臺/記憶/摘要可能互相擠壓。
- 落點：`agents/agent_mod/chat_agent.py::_build_context_str` 後加 `trim_context_to_budget()`；順序：保 system 契約 → 丟最老對話 → 截單段，保留當前輸入與 owner 當前句。
- 注意：不能把 user 當前輸入截成 0；不能為了預算砍掉【主人此刻】最新一句。

### E. PASS／短句本地池（只借「決策與措辭分離」）

- 來源：Pallas `low_engagement.py:139-153`；三層過濾（≤12 字、無問句、無 CQ）。
- 我們現況：她的「要不要說」與「說什麼」綁在同一個生成；沉默與主動訊息都靠模型。
- 可借：把「這一輪要不要接」做成代碼決策（回/不回/只給語氣詞），再由模型或本地池產生一句；短句池要按我們人格重寫，不能抄 Pallas 的「笑死我了」。
- 風險：容易變成復讀機；先 shadow，不直接上。

### F. LLM 文本加工的保真校驗

- 來源：MaiBot `llm_sentence_splitter.py:114-138`（忽略空白重建比對，失敗報首個差異位）。
- 我們現況：q3 融合、摘要、反思都會「改寫」；沒有「改寫後必須與原文等價」的檢查。
- 落點：先用在引用回覆（`reply_context`）與摘要（`session_watcher`）；不做全鏈。
- 注意：我們很多加工是容許改寫的，不能一律套；只套「只能切、不能改」的場景。

- 231 個 prompt×三語、prompt 原文當字典鍵、非 strict placeholder：維護災難，且我們已吃過提示詞漂移的虧。
- A_Memorix 整座 SQLite＋圖＋PPR＋LLM 自動抽 fact：重、且我們已被 3B 抽取污染過；只借 claim/evidence/transition 的 schema 思想與 alias 表。
- Pallas 五個近似協調原語、Redis claim、多 Bot/多分片：我們單進程單 GPU，過重。

- 大量 plugin/ACP/MCP/desktop pet：不是現階段。

## 5. 我們現在最大的「代碼沒兜住」

不是模型笨，是**最終輸出前沒有最後一道 deterministic 清理與白名單**。
今天 17:24 水汽、17:30 把自己的話說成主人、19:22 回聲、問句尾巴 13/27，這些不是單一 prompt 能修；其中至少「多餘前後綴、markdown、URL、重複句、過長、問句尾巴」可以在發送前用代碼擋掉或降級。這與 07 的 21/29 結論一致。
