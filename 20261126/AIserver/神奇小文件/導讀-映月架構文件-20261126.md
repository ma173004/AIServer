這七份文件不是七個互不相干的架構，而是同一個系統在一個月內留下的不同切片：

- 有些是**現在的程式真的在跑**（20261125、20261113、20261110）。
- 有些是**盤點＋提案**（20261116）。

「總感覺沒修好」有一部分原因就在這裡：文件混了「現況」「目標」「舊草案」，而實際 code 只實作了其中一部分。這幾天修的 P06／P30／coverage 是**可觀測性與訊息生命週期**，不是對話品質本身；對話品質那幾層（context、記憶、思考迴路、輸出約束）還在改到一半。

## 二、現在真正在跑的架構（按一輪對話的順序）

### 1. 入口與回合

```
Discord / Web
  → agents/dshmid.py（HTTP / SSE 中間層）
  → audience 回合鎖（owner / guest）
  → MIMO 合併窗（預設 700ms）
  → pipeline：decompose → judge → executor（chat / task / research / …）→ fusion / q3 → reply
```

2026-11-25 補了 **P06 訊息生命週期**：

- 每條 owner 訊息有 `turn_msg_received`、collector／queued／replied／finish_shadow。
- Phase 1A：owner-scoped finish、queued 原文、`turn_msg_replied` 終態。
- Phase 1B：coverage shadow 記錄這一輪收了哪些訊息、回了什麼。
- 但 **carried／re-queue 還沒做**，queued 訊息仍可能只被清掉、不被回覆。

### 2. 編排層

- `agents/diaoyongai.py`：q1 拆解、q3 融合、所有 Ollama 呼叫。
- `agents/executor.py`：跑子任務、局部重規劃、融合。
- `agents/agent_mod/*`：chat / task / research / writing / learning / work / code / generic 各自的生成 prompt。
- 這層的問題：decompose 會把閒聊誤判成 task（例如「我上學去了」→ 查手機前台 app），judge 只判斷「類型／意思／不確定」，沒有 speaker／evidence 的硬檢查。

### 3. 上下文組裝

`chat_agent._build_system_prompt` + `_build_context_str`：

- system（≤2000）：人格 + 契約 + 場景 overlay。
- user context：時間與場景、主人此刻、我此刻、我先讀懂主人這句、工作臺、歷史摘要、事實卡、對話、提示、歷史記憶、我正在想、當前輸入。
- 問題：多個區塊都可能是舊的（快照、摘要、自己的 proactive、after_turn 推論），但沒有統一的「這條資料從哪來、可不可信、有沒有過期」標記。

### 4. 記憶與狀態

- Hindsight：master（目前凍結寫入）、guests、archive、text；master2 尚未切換。
- 本地狀態：`runtime/dialogue/`（對話線）、`runtime/self/thoughts.jsonl`（思考）、`runtime/self/continuity.jsonl`（連續思考紙條）、`workspace/workbench.md`（工作臺）、`runtime/self/questions.jsonl`（問題清單）、`runtime/experience/`（經驗卡）。
- 問題：這些狀態會回灌到下一輪 context；舊的、錯的、測試留下的內容沒有被清掉時，就會變成她下一輪的「事實」。

### 5. 側迴路（不參與本輪生成，但會寫下一輪）

- `thought_loop.py`：idle 思考、after_turn、會產生 say／continuity。
- `dialogue_thread.py`：回合後反思（after_turn）、對話線。
- `mind_loop.py`：每 3 分鐘的背景思考。
- `self_questions.py`：問題清單（目前 300 條、大多 open）。
- `outbox.py`：主動訊息。

這層是「她自己的聲音」的來源，也是今天幾個 bug 的來源：她自己的 proactive 被下一輪當事實、after_turn 推論被寫進 continuity、自己的話被誤認成主人說的。

### 6. 可觀測性

- `agents/logs/trace/*.jsonl`：每輪 stage（decompose / judge / chat / executor / turn_done…）。
- `runtime/shadow/turn_msg_attribution.jsonl`：訊息生命週期＋coverage shadow。
- `runtime/shadow/evidence_ledger.jsonl`：每輪實際注入的 context 區塊與來源。
- `/coverage`：人工標 answered／acknowledged／ignored／misread。
- `/turn`、`/timing`、`/shadow`：其他診斷頁。

這是這幾天花最多時間的地方；它讓問題可見，但不會自動讓對話變好。

## 五、讀完後最值得問的三個問題

1. **哪一層是「輸入」、哪一層是「輸出」？**
   現在很多 bug 是輸入被污染（舊快照、自己的 proactive、測試記憶），不是輸出 prompt 寫錯。

2. **哪些架構已經實作、哪些只是設計？**
   四管道、brief-lite、carried、P29 append-only 都還是設計；不要把它們當成現在的行為。

3. **如果只能先修一層，修哪層？**
   我會選「輸入資料的來源與過期標記」：先讓每一塊 context 都帶來源、時間、可不可信；這比再加一條 prompt 更接近根因。
