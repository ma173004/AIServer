## 一、記憶庫是什麼

**一句話：記憶庫 = 映月的「長期事實檔案館」，不是聊天記錄。**

- 實體：Hindsight（本地容器，:8888）的 bank（庫）裡的一條條 **fact（事實節點）**，用主題/關係圖連起來（semantic / temporal / entity 三種邊）。
- 每條 fact 有：內容、時間、tags（`topic:*` / `scope:*`）、fact_type（world=穩定屬性 / experience=事件經歷）、來源 document。
- **庫是分區的**（bank 不是只有一個）：
  | bank | 用途 | 現況（2026-10-25 21:50） |
  |---|---|---|
  | `master` | 主人本人的長期記憶（正式庫） | 36 條事實、11 條 observations、3 份文件 |
  | `guests` | 客人的記憶，按客人標籤隔離 | 19 條、18 份 |
  | `archive` | 歸檔的對話輪次（不污染 master） | 58 條、13 份 |
  | `text` / `test3b` / `bench-extract` / `knowledge_probe` / `mind-lab*` | 測試/評測用，正式不用 | 0–14 條 |
- **寫入流程**：對話輪次 → retain（非同步）→ 抽取模型（3B）把輪次壓成 facts + observations → 寫進 bank。
- **讀取流程**：需要時按查詢召回 → 相關性過濾 → Memory Worth 閘門 → 最多 8 條注入【歷史記憶】。
- **沉澱認知（observations）**：把 facts 再抽象成「關於人物/項目的穩定結論」。master 已開，現有 11 條；目前**只存不讀**（未注入），是下一步要用的資源。

## 二、短期記憶是什麼

**一句話：短期記憶 = 這一輪對話還「在桌上」的東西，不是資料庫。**

三件東西：
1. **對話窗口**：`runtime/session_log.jsonl`（最近 16 條訊息，日誌本身常被歸檔清空）。
2. **摘要**：`runtime/session_summary.json`（最近幾段對話的精簡要點，3B 生成、14B critic 校驗），現 831 字、3 段（10-25 13:26 / 19:42 / 20:43）；歷史摘要 15 段。
3. **注入預算**：每輪最多 6000 tokens 估算（`SESSION_MAX_TOKENS`），超出就淘汰最老輪次；閒置 30 分鐘（`SESSION_IDLE_TIMEOUT=1800`）就歸檔：摘要保留 + 輪次進 `archive` bank。

**它跟記憶庫的分工**：短期記憶負責「現在在聊什麼」，記憶庫負責「他是誰、發生過什麼」。短期記憶一被清掉，接續就靠摘要 + 記憶庫召回。

## 三、工作臺／日記是什麼

- **日記（diary）**：映月自己的第一人稱記錄。觸發靠 gate（事件強度/明確指示），2B/14B 寫成 25–90 字 + 心情（mood），每天最多 2 條。
  - 存放：`runtime/diary/entries.jsonl`（結構化）；**她可讀的工作臺**：`workspace/diary/YYYY-MM-DD.md`。
  - **默認不注入**（`diary.inject=false`）：這是她的東西，她輸出 `<read_diary/>` 才看。
- **工作臺（workspace）**：她自己的筆記本。日記是其中一部份；另含 notes、projects、上傳/截圖等。意義是「跨回合、跨會話的連續存在」：她隨時可以讀寫自己的檔案。
- **理解（mind）**：每 24 小時從 master 事實 + 日記蒸餾出「對主人的理解」（≤460 字），常駐注入：現在她對主人的認知不是一條條記憶，而是一段描述。
- **現況**：日記 3 條（10-24 兩條、10-25 一條，例：颱風夜「總得有人說句實話」）；工作臺已回填 10-24、10-25 兩天 md；但 md 內仍有同日近重複（00:20 與 00:46 颱風夜）需清理。

## 四、工程原理（為什麼這樣設計）

1. **分層而非大一統**：事實庫（Hindsight）／短期窗＋摘要／日記＋工作臺＋理解，四層各有職責、各有預算。單一層不能同時承擔「全量」與「每輪注入」。
2. **寫讀分離**：寫入是非同步抽取（不阻塞回覆）；讀取是確定性召回＋閘門（不讓模型幻覺記憶）。「記住什麼」與「用什麼」是兩個決策。
3. **注入是稀缺資源**：每輪記憶注入有硬上限（8 條 / 約 1200 tokens），寧少勿濫；相關但無效的記憶會擠佔上下文並損害回答（Memory Worth 就是為此）。
4. **記憶價值閉環**：每條記憶維護檢索次數與被檢索後的成功/失敗計數 → value；低價值且久未用 → 降權/休眠（可達性衰減，不是刪除）。
5. **歸檔不丟棄**：歸檔輪次進 `archive` bank，不進 master；摘要永久保留。分離防止「替換會話」污染主人記憶。
6. **她能自己查**：日記是她的選項（`<read_diary/>`）、知識是她的工具（`<lookup>`）、記憶召回由系統在需要時提供——逐步從「系統替她決定」轉向「她能自己意識到要查」。
7. **可觀測**：每個請求是一個 Episode（唯一 id、只追加、可回放）；記憶頁面可看「本輪會注入什麼」；/health 有記憶指標。

**缺口（按優先級）：**
1. **日記太少**：3 條 / 2 天——gate 偏嚴 + 只在明確事件時寫；工作臺內容單薄。
2. **工作臺同日去重未完成**：md 裡 00:20/00:46 重複仍在（jsonl 已清）。
3. **worth 只記成功**：outcome 全是 ok=true → value 單調樂觀、閘門空轉（`mem_worth_skip` 命中 0）。
4. **observations 只存不讀**：11 條沉澱認知沒有進入召回/注入。
5. **召回質量未量化**：沒有 recall precision/recall 指標；記憶多時是否真能挑對，未驗證。
6. **短期窗剛重置**：session_log 為空，摘要只有摘要段；跨會話連續性仍偏弱。

## 六、預期目標

**短期（1–2 週）**
- 日記穩定每天 1–2 條、工作臺去重、日記品質評測常態化。
- worth 接失敗信號（自審失败、honesty 改寫、用戶糾正）→ 閘門真正生效並調閾值。
- observations 進入召回（作為「高層摘要」優先注入）；召回加評測集（20 條查詢，量 precision）。
- 短期窗與摘要預算調優（16 條/6000 tokens 是否合適）。

**中期（1 個月）**
- 三層合併注入：摘要 + 日記 + 理解 + 召回，統一 token 預算與優先級。
- 記憶價值閉環：記憶→檢索→成敗→價值→衰減/淘汰，形成可解釋曲線。
- 主動遺忘：降權不刪、休眠可恢復；可視化「哪些記憶在衰退」。

**長期**
- 人格化記憶：情緒標籤、時間衰減曲線、情節鏈（一段關係的來龍去脈）。
- 她自己的記憶主權：能自己決定記什麼、查什麼、忘什麼（工作臺 + 日記 + 檢索工具）。
- 可追蹤：每條記憶都能回放到來源 episode。
