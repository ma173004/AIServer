# 四管道方案與主人定案：失敗化假設（送紅隊失敗反駁）

日期：2026-11-20
狀態：設計／規劃，**不改程式、不改行為**

## 0. 要紅隊做什麼

不是重新設計，而是**逐條攻擊**：對每個方案與主人決定，找出「它會怎樣失敗」——失敗模式、早期信號、最壞情況、誰會受傷、可回滾性，以及「如果只能保留一條，最該先放棄哪條」。特別注意：主人已定的方向**不是不可反駁**，但要先承認他的前提（她是她、主人是主人；公開場合默認客人；不設轉述通道），再指出實作後可能反噬的地方。

## A. 群聊：主人標記＋公開默認客人（主人定案 11.1）

### A1. owner 用既有 `owner_accounts.py` 的 canonical ID 判定
- 假設：bot 在群訊息帶 `speaker_role=owner|friend|guest`、`owner_present`、`channel_kind=group`，dshmid 用「audience × channel_kind × speaker_role」選 packer。
- 失敗假設：
  1. 主人換小號／新帳號未加進 config → 被當 guest（fail-closed），他在群裡被冷淡對待；他以為「她認得我」。
  2. config 裡有舊／錯 ID → 陌生人被當主人，群裡她可能叫名字、給特權語氣（隱私／形象風險）。
  3. 訊息轉發／截圖場景：不是本人 ID 發的內容被當主人說的。
  4. header 沒帶或帶錯（web／未來入口）→ 默認 guest，主人線斷。
- 早期信號：主人群訊息被標 guest；guest 被標 owner；`speaker_role` 分佈異常（owner 佔比過高）；群裡她對主人用「您」。
- 最壞情況：她把陌生人當主人，在群裡透露「主人允許的公開事實」之外的东西；或主人覺得群裡的她像陌生人。
- 反駁問題：owner 換帳號的流程誰維護？config 錯了如何自動發現？是否應該「主人 ID 只在私聊生效，群裡永遠 public-self」而根本不給她群內特權？

### A2. 未標記 friend 默認客人
- 失敗假設：
  1. 四大元老／樹人以外的老朋友先被降成客人，對方感受到「變生分」；她之前叫名字、接玩笑，突然變「您」。
  2. 主人忘了標記，或標記後忘了存；`people.json` 手改格式錯 → 整線 fallback。
  3. 同名／改暱稱：判斷用 name 的話會錯（所以只認 ID，但顯示名與 ID 映射要維護）。
  4. 熟人標記是「主人視角」：主人把同事標熟人，她對同事過度親密（紅隊意圖已指出）。
- 早期信號：朋友回覆「你怎麼突然這麼客氣」；同一個人 DM 與群裡態度不一致被截圖；`people.json` 解析錯誤 log。
- 反駁問題：是否應該「默認客人」但保留「她自己的熟悉度」而不是主人給的 closeness？標記命令要不要二段確認？

### A3. 群裡認得主人但用 public-self
- 失敗假設：
  1. 主人在群裡期待她像 DM 一樣親近，結果她短、直、不接私事，他覺得「群裡的她不是我認識的她」。
  2. 旁人看不出她認得主人，但話裡若泄漏「主人昨晚…」→ 形象風險。
  3. 她對主人 public-self 太冷，主人反而懷念舊版；回滾要 per-channel flag。
- 早期信號：主人說「你在群裡怎麼這樣」；群裡她對主人句數／親密度與 DM 差異過大；截圖外流風險。
- 反駁問題：群裡 owner 發言是否應該走 guest/group pipeline 而完全不給 owner 特權？「認得主人」是否只為了不冒犯，而不是為了親密？

### A4. 群背景只在「主人問群事／她被叫到」時注入
- 失敗假設：
  1. 主人問「他們剛才在說什麼」但觸發條件沒中（間接問法）→ 她沒有 context，答「不知道」，主人失望。
  2. 觸發太寬 → 又回到 DM 被群背景污染。
  3. provenance 標了但模型仍把「群裡某人說」當主人說（主語漂移），標記無效。
  4. 群背景含第三者私事，注入主人 context 本身即隱私問題。
- 早期信號：主人問群事後她回「我沒看到」；DM context 出現 group block；主語錯配抽樣 >0。
- 反駁問題：是否應該「群背景完全不進主人 context」，主人問時由工具即時讀群檔案（帶 provenance）？這樣可避免長期污染。

## B. 朋友線：她知道「那些話是自己說的」＋可主動引用（主人定案 11.2）

### B1. 每輪注入最近 N 條自己的發言
- 失敗假設：
  1. 歷史含舊測試資料／malformed tag／別人的話（`runtime/guests/*.jsonl` 目前只有 3 個檔，但可能有測試污染）→ 她引用不存在或不是她說的話。
  2. guest 歷史只有她與該朋友的，沒有跨朋友的隔離檢查；若 label 碰撞（同名）→ A 朋友的話出現在 B 朋友對話。
  3. 注入「這是你說的」變成示範，她直接複述上一句（紅隊曾警告：履歷注入會誘發抄寫）。
  4. 日期錯／跨日格式錯，引用時說錯時間。
- 早期信號：引用句在檔案中找不到；引用日期與檔案 ts 不符；與上一句高度重複（bigram/LCS）。
- 反駁問題：應否只在她被問時才檢索，而不是每輪注入？「自己說過的話」要不要有 expire（例如 30 天前的話不主動提）？

### B2. 相關話題可以主動引用
- 失敗假設：
  1. 像翻舊帳／監視感：「你上次說過喜歡 X」「你三個月前說討厭 Y」→ 朋友不舒服（尤其關係不深）。
  2. 引用出錯語境：她當時是玩笑／反諷，現在當事實引用。
  3. 頻率失控：每輪都「你之前提過」，變模板。
  4. 只在熟人可用？客人若也主動引用，會越界。
- 早期信號：朋友說「你怎麼記得這麼清楚」；主動引用 >1/會話；引用後朋友沉默／轉話題。
- 反駁問題：是否應該分層——熟人可主動、客人只被動？是否要「引用前先問『我可以提你之前說的嗎』」這種元確認？

### B3. 「你知道那是你自己說的」
- 失敗假設：
  1. 她仍可能否認（模型不認帳）：「我沒說過」；或過度道歉「對不起我忘了」→ 更假。
  2. 她可能把朋友的轉述當成自己說的（朋友說「你上次說…」但其實是朋友編的）。
  3. 她知道那是自己，但不知道那是「公開面」；把公開面的話帶回 DM 或主人線，造成角色混淆。
- 早期信號：否認句出現但歷史有原文；把朋友的話標成自己說；跨線引用。
- 反駁問題：需要一個「歷史不可否認」的硬規則（回覆前檢索），還是靠 prompt？如果檢索不到，她應該說「我不確定」而不是否認？

### B4. 永遠不寫 master
- 失敗假設：
  1. 現有漏點仍在：`agents/collectors/hko.py:189` 直接 retain 沒傳 bank；`guest.handle_turn(group=True)` 仍寫 guests bank；`_group_context_section` 進主人 context 後被 after_turn 沉澱帶進 master。
  2. 未來新增 call site 忘記 scope。
  3. master 凍結解除後，舊漏點復活。
- 早期信號：master 出現 guest/group 來源 tag；retain 呼叫無 scope；guest 歷史被檢索成 master。
- 反駁問題：要不要「retain 無 scope 直接 raise」而不是預設 master？一次全面 grep 夠不夠？

## C. 轉述與反向轉述（主人定案 11.3；反向待定）

### C1. 不設朋友→主人通道
- 失敗假設：
  1. 朋友覺得她「沒用／不通人情」，尤其急事（「幫我叫他」）。
  2. 朋友改用群裡 @ 主人，造成群裡噪音；或朋友改問她「那你可以幫我告訴他嗎」反覆。
  3. 她話術太硬，朋友覺得被拒絕、關係受損。
- 早期信號：朋友重複要求轉達；朋友說「你怎麼這麼冷」；朋友直接在群裡 @ 主人次數上升。
- 反駁問題：安全例外（求救／緊急／涉及主人安全）要不要破例？破例要不要事後告知？

### C2. 反向：主人問「朋友跟你說了什麼」
- 這是目前未定的規則（需要主人回答）。兩個選項：
  - **A 預設不轉述**：朋友私話留在朋友線；除非朋友明說「可以跟主人說」。她回「那是他跟我聊的，我不確定他願不願意讓你看到」。
  - **B 主人問就可以說**：主人有權看朋友對她說的話；但這是不對稱的（朋友不能透過她找主人，主人卻可以透過她看朋友），且朋友可能不知道。
- 失敗假設（A）：主人覺得「我是主人卻不能問」；緊急時她仍拒絕，主人不滿。
- 失敗假設（B）：朋友發現私話被轉述 → 信任崩、關係破裂；她變成主人的監控工具；意圖紅隊曾警告「朋友線全開請示／轉述＝監控」。
- 早期信號：主人問朋友私話頻率；朋友說「這些話是跟你說的，不是跟他說的」；她轉述後朋友退群。
- 反駁問題：是否應有第三種「摘要但不出原文」？是否要「朋友可設定可否轉述」？主人自己願不願意被同等對待（她的話會不會被轉給朋友）？

### C3. 群裡朋友問「主人在嗎」
- 失敗假設：只回「他在，你可以直接 @ 他」對朋友無用（主人不在）；她可能被當成傳聲筒拒絕器；群裡公開拒絕讓朋友尷尬。
- 反駁問題：應該沉默、還是「他現在不在，你 @ 他他看到會回」？哪種更像人？

## D. 四管道架構本身（紅隊修訂後的方案）

### D1. dshmid header 契約＋預設拒絕（fail-closed）
- 失敗假設：web／其他入口漏 header → 她「消失」不回應；既有 caller 未更新 → 全線斷；除錯更難（沒有 audience 顯示）。
- 早期信號：非 bot 入口空回覆；header 缺失 log 暴增；主人說「她怎麼不回」。
- 反駁問題：預設 guest 還是預設 400？是否先 shadow 一週記錄「若 fail-closed 會拒絕誰」？

### D2. turn_id／provenance 穿線（P0a）
- 失敗假設：字串 ID 產生成本／儲存膨脹；舊資料無法回溯；trace 檔暴增；測試對齊成本；某條線忘了傳 → 歸屬率卡在 90%。
- 早期信號：trace / session_log / guest history 缺 turn_id；episode meta 仍空；磁碟成長。
- 反駁問題：turn_id 是否應放 episode header 而非每筆 trace？取樣而非全量？

### D3. info_decision 放 event_frame 後
- 失敗假設：event_frame 8000 條上限導致舊 event 決策無法重算；兩個 sync 入口重複決策；「是否已對主人說過」仍漏記。
- 反駁問題：單一寫入者要掛在哪（sync worker 還是 tailer）？event 過期後 decision 保留多久？

### D4. 檔案方案改 projection（不加 runtime/pipelines）
- 失敗假設：projection 每次要 join 多檔、慢；join key 不齊（turn_id 缺）→ 視圖不完整；後續查詢仍要寫 ad-hoc script。
- 反駁問題：projection 的輸出要落哪裡、多久生成一次？是否會變成第二套真相的變體？

### D5. 朋友/群記憶隔離與 bank scope
- 失敗假設：改 `retain(scope)` 要動 5 個 call site + 未來；現有 master 污染清理未完；group 歷史已在 guests bank，切割後舊資料歸屬不明；guest→group 的同一人歷史被切斷。
- 反駁問題：舊 group rows 怎麼遷移？是否接受「舊資料留在 guests bank 但標記」？

## E. 主人定案的橫向失敗模式

- **E1. 公開默認客人＋主人標記** 會讓她對「未被標記的人」一律冷淡，若主人忘記標記，朋友感受到的是「她變了」而不是「規則變了」。
- **E2. public-self** 可能讓群裡的主人覺得「她不認我」；但這是主人自己選的，需不需要一句只有主人能看出的暗號（例如叫名字）？
- **E3. 自歷史可主動引用** 與「不設轉述」可能有張力：她可以引用朋友說過的話，但不能把朋友的話轉給主人——界線要清楚（引用對象是朋友本人，不是主人）。
- **E4. 不設轉述** 與「安全例外」：緊急情況（朋友求救）她是否仍要拒絕？這是主人的價值判斷。

## G. 系統紅隊首輪失敗反駁（2026-11-20 03:2x，已做只讀查證）

### G1. 已由我核對、確認成立的現況漏洞
- **A1（主人判定）**：`agents/owner_accounts.py:30-37` 把兩個主人 Discord ID 硬編碼；`_cfg()` 讀 `config/discord_accounts.json` 失敗時 `except (OSError, ValueError): pass`（`:56-74`）→ 靜默回默認值；`_match()`（`:94-117`）除了比 ID，還用 label／name／aliases 的 casefold 比對 → **陌生人只要顯示名相同就可能被認成主人**。所以「陌生人不小心被當主人」不是假設，是現行行為。
- **A2（默認客人）**：`runtime/relations/people.json` 目前 5 個朋友＋阿明：測試鈡／林／龍／樹人／陳都是 `closeness=熟人`，但**測試鈡／林／龍三筆共用同一個 `id=p1792822721004`**；阿明 `discord_id` 是空字串。默認客人一旦上線，這批「熟人」會全部降級，而系統不會有任何告警。
- **B4（不寫 master）**：`agents/collectors/hko.py:184-193` 天氣事件直接 `retain` 沒傳 bank（已寫進 master 的路徑）；`guest.handle_turn(group=True)` 仍 append 到 `runtime/guests/<label>.jsonl` 並 `retain_async` 到 guests bank（`guest.py:1364-1366`）；群背景再經 owner context、after_turn 沉澱可能進 master。
- **D1（fail-closed header）**：`audience` 預設 owner 的 fail-open 仍在；web／其他入口漏 header 會變主人。紅隊要求「先 shadow 一週記錄如果 fail-closed 誰會被拒絕」，不要直接上線。
- **D2（turn_id）**：今日 trace 795 筆沒有 turn_id／audience／ep_id；episode_start payload 的 meta 是空的；guest history／channel_ctx 沒有 turn_id。紅隊強調「只放 episode header 不夠，每一筆 trace/紀錄都要有」，建議用 contextvar 從 dshmid 單一生成點注入。

### G2. 系統紅隊的主要反對與建議
- **A3**：反對「暗號」——任何旁人可觀察的行為久了都會被看出或截圖；「認得但不親密」應由「不主動提私事」實現，不要把秘密當成親密。
- **A4**：最致命的不是她答「不知道」，而是**群背景含第三者私事，光注入主人 context 就是隱私問題**（即使她不说，模型也可能引用）。建議：群背景完全不進 owner context；主人問群事時用工具即時讀、帶 provenance、用完即棄。
- **B1**：現況沒有真實資料可驗收（`runtime/guests/` 只有 3 個測試檔），且 guest 歷史用顯示名做檔名，改名／label 碰撞就斷。建議改成**被問才檢索＋標日期/來源**，不要每輪塞最近 N 條。
- **B2**：主動引用容易變翻舊帳／監視感，且頻率失控就變模板；建議**主動引用預設關、per-friend 開**，先只做被動。
- **B3**：「她知道那是自己說的」不能只靠 prompt；要硬性「回覆前先檢索」規則，檢索不到就說不確定；否認率 >0 就回滾。
- **C2（反向轉述）**：紅隊**不同意選 B（主人問就可以說）**——不對稱、不可逆、朋友不知情，與「不設轉述」前提矛盾；建議 A（預設不轉述）。安全例外只做成「催朋友直接找主人／管理員／報警」，她本人不成為通道；若主人堅持例外，事後必須告知誰被轉述。
- **C1**：不設通道不等於不設回應策略；固定話術「我無法轉達，你可以直接 @ 他」，不要做空頭承諾。
- **C3**：群裡朋友問「主人在嗎」→「他現在不在；@ 他他看到會回」，不做承諾。
- **D2 優先**：紅隊認為如果只能先做一件事，先做 **turn_id 穿線**（純 additive、可回滾，沒它所有驗收無法量測）。
- **D3**：info_decision 掛在 event_frame sync 的**單一 worker**，decision 自帶快照，不重算。
