# 四管道分揀設計（2026-11-20，主人 m48274）

> 目標：把「主人／朋友（客人）／信息／群聊」四條管道拆清楚——
> 每條**必須有什麼、不能有什麼、靠什麼分開、檔案結構怎麼編排**。
> 本文是設計與盤點，不是已實作；先給兩隊紅隊反駁，再排最小落地順序。

## 0. 原則（先立規矩，避免又長成一個大 agent）

1. **共用「她是誰」**：人格核心、模型呼叫入口（含優先級／preempt）、記憶治理（evidence／denylist／promotion）、安全與隱私、回覆渲染（繁中／格式／假動作防護）、審計與 faults。
2. **不共用「對誰能說什麼、能做什麼、看到什麼」**：每條線有自己的 context packer、speak/action 權、provenance 規則。
3. **入口分流在 dshmid 之前**：`audience`（owner/guest）與 `channel_kind`（dm/group）在第一跳就決定，不靠 prompt 裡的「你是客人」。
4. **每條線的產物不互相回灌**：朋友／群的對話不得寫進 master；信息不得寫成「她的經歷」；群聊沉默也是一種合法輸出（不生成＝零成本）。
5. **檔案按線分開**，但格式共用（JSONL、UTC ts、source 欄位），讓跨線審計與重播可以做。

## 2. 逐管道：必須有／不能有／如何分開

### 2.1 主人線（owner）

**必須有**
- 身份：主人（大號／小號 canonical）；人格 v9；契約三層（信息優先級／失敗回退／四步）。
- Context：最近對話（含引用 X-Reply-Ctx）、master 記憶（含關係）、【主人此刻】（>24h 降級）、【我此刻】去空動作、工作臺三節（已精簡 201 字）、提醒清單、歷史摘要（只留主人原話行）、T6 表達 overlay、channel sender 身份。
- 權限：主動訊息（outbox）、followup、T6 行動傾向、自我工作臺、問題清單；查主人位置／手機／校曆（唯讀）。
- Provenance：每一塊 context 標來源；外部資料固定寫「系統／採集告訴我」。

**不能有**
- 朋友或群聊的私事直接進 master 或主人 context（只能透過「主人自己說過」或受控轉述）。
- 群聊頻道上下文無條件注入主人回合（現在 `_write_group_context_file` 有 5 分鐘注入機制，需檢討邊界）。
- 採集資料以第一人稱經歷出現（「我看到你上線」→「系統顯示你上線」）。
- 未經主人同意的長期追蹤（位置僅快照、不常駐監控）。

**如何分開**
- 入口：`X-Audience=owner`；主人大小號 canonical_speaker；非 owner 不進此線。
- 記憶：只讀 master；寫入走 `memory.remember_now`／反思沉澱（現已凍結寫入待清污）。
- Context packer：`chat_agent._build_context_str` 按區塊組裝；每塊有 source_type。
- 輸出：主人 line 可主動；其他線不可。

**檔案（現況／目標）**
- 現況：`runtime/archives/<date>.jsonl`、`runtime/dialogue/owner_main.json`、`runtime/self/thoughts.jsonl`、`runtime/self/continuity.jsonl`、`runtime/memory/…`、`workspace/workbench.md`。
- 目標：`runtime/pipelines/owner/`（turns.jsonl／context_snapshots.jsonl／decisions.jsonl）＋既有檔不搬，先用索引。

### 2.2 朋友（客人）線（guest）

**必須有**
- 身份導入：這位朋友是誰（名字／display name）、與主人關係、主人希望的態度距離（closeness：熟人／客人）、我能叫他的名字（不要「客人」）。
- 關係卡：`runtime/relations/people.json` 的 closeness、last_seen、interaction count；態度具體化（熟人：自然、可接玩笑、問近況；客人：禮貌、只答、不追問）。
- Context：朋友模板（靜態 system）＋動態 user message（這位朋友、熟悉度、情景、時間、頻道、guest bank 記憶、工具結果、頻道最近消息、最近對話、本輪話）。
- 權限：只回應；可查公開資訊（天氣／路線）；不能查 master、不能查主人位置/行程、不能操作主人裝置。
- Provenance：guest 對話寫 guests bank，不寫 master；`guest_sanitize` 過濾主人私事、第三人、跨頻道。

**不能有**
- master 記憶、主人此刻、我此刻、工作臺、continuity、thoughts、問題清單（她自己的內心生活不進客人線）。
- 主動訊息／followup／proactive；朋友線不應「半夜想他」。
- T6 全局 knobs 被朋友對話拉低（AVP 只做事件暫態、audience overlay，20–30 分衰減）。
- 冒充主人（主人 2026-11-20 澄清：她是她、主人是主人；但她的言行影響主人名聲）。
- 空頭承諾（「我幫你查」但沒查）、未查證的具體數字／年份／評分。

**如何分開**
- 入口：`X-Audience=guest` + `guest_id`；dshmid 在 `affect.tick` 前就 `guest.handle_turn`（目前是這樣，天然隔離）。
- 記憶：`recall_guest_memories` 只查 guests bank；不碰 master。
- Context packer：`guest.build_system_prompt`（靜態）＋`_build_context_parts`（動態 user message）。
- 輸出：只回原頻道；`guest` 有自己的 rate limit（3s／日 200）。

**檔案**
- 現況：`runtime/guests/<slug>.jsonl`（歷史）、`runtime/guest_ctx/channel-*.jsonl`（頻道上下文）、`runtime/relations/people.json`、`config/guest_scenes.json`、Hindsight guests bank。
- 目標：`runtime/pipelines/guest/`（turns／context_snapshots／decisions），`runtime/guests/<slug>.jsonl` 保留。

### 2.3 群聊線（group）

**必須有**
- 頻道材料：最近 N 條訊息（speaker、時間、是否回覆誰、quote）、`mentions_me`、`owner_present`、`channel_policy`（可讀/可回/唯讀）、群組名稱。
- 這句在說誰：規則先解 target（reply_to 作者→@→叫名→speaker）；只有代詞／第三者歧義才叫一次模型；輸出 target／confidence。
- 身份：朋友模板＋群聊讀法＋她自己的名字；「她是她，但別人對她的印象＝對主人的印象」。
- 權限：被 @／回覆她／叫名才回；**沉默是預設**（非 @、沒問她、涉私事、需權限、語境不明 → 不回，只記錄）。
- 邊界：不替主人承諾/決定；不洩主人私事；被問主人時只轉述公開事實或請對方直接問主人；不假裝主人。

**不能有**
- 把全群當主人、對每句都回（目前「每句問句收尾」的榨話風險）。
- 主動關心未被 @ 的群眾（先不做，另案）。
- 群聊內容寫入 master 或朋友記憶（只進 channel log）。
- 對空氣回話（target 不明卻硬回）。

**如何分開**
- 入口：discord_bot `GROUP_ADDRESSED_ONLY`；未 addressed 只 `_group_parse_observe`（shadow，不發送）。
- Context packer：`group_ctx_current.json` 只 5 分鐘注入；`guest_context` 字串需結構化（現已有 `group_parse` shadow）。
- 記憶：只讀 channel log；不寫 master/guest bank。
- 輸出：原群組；沉默不生成。

**檔案**
- 現況：`runtime/guest_ctx/channel-*.jsonl`、`runtime/group_ctx_current.json`、`runtime/shadow/group_parse.jsonl`。
- 目標：`runtime/pipelines/group/`（channel_turns／parse／decisions）；`group_parse` shadow 先跑。

### 2.4 信息線（info）

**必須有**
- 接收：collectors → `runtime/collect/items.jsonl`＋`*_current.json`；event_frame 信封。
- 解析：正規化（時間／地點／數值／來源／重要度）；失敗／skipped 要記錄（已修）。
- 可用度（`info_decision`）：`collected` → `usable` → `sayable`；欄位：evidence、freshness/TTL、certainty、sensitivity、owner relevance、actionability、repeat。
- 是否輸出／記錄：預設 record；只有四條件齊（與主人直接相關、主人能回應、她可確認、時效內）才進 sayable；否則只留檔／digest。
- 使用：①背景思考（mind_loop 事件，已加時效過濾）②主動訊息候選（未來）③注入主人 context 的「系統資料」。
- Provenance：資料一律標「系統/採集告訴我」，不得寫成「我看到／我去過」。

**不能有**
- 把「採集到」當「可用」，把「可用」當「該說」。
- 無時效事件、無來源數字、無可信度分級。
- 寫入 master 或她的連續思考（self/experience/continuity）。
- 資訊變成假經歷（「我剛看過」「我去過」）。
- 每條採集事件都通知主人（噪音）。

**如何分開**
- 入口：collector_daemon（獨立 thread/process），不經 chat。
- 轉換：`event_frame.sync_from_collectors` → `external_events.jsonl`（已恢復 worker）。
- 決策：`info_decision` 純函數（shadow），只寫 `runtime/info/info_decisions.jsonl`。
- 消費：mind_loop `_events_brief`（已過濾 stale）；主人 context 只注入經 info_decision 的 sayable（未來）。
- 輸出：未來由主人線說出（「天文台說…」），資訊線本身不發訊息。

**檔案**
- 現況：`runtime/collect/{items.jsonl,*_current.json,state.json}`、`runtime/events/external_events.jsonl`、`runtime/events/frame_dedupe.json`。
- 目標：`runtime/pipelines/info/`（collected／decisions／sayable），`runtime/info/info_decisions.jsonl`。

## 3. 跨線共用與隔離清單

| 元件 | 共用？ | 說明 |
| --- | --- | --- |
| 人格核心（prompts/persona） | 主人全用；朋友/群用 guest 模板 | 不共用「關係細節」 |
| 模型入口 `diaoyongai.call_ollama` | 共用 | 含 priority／preempt；各線不可繞過直呼 11434 |
| 記憶治理（evidence/denylist/promotion） | 共用程式，**bank 隔離** | 主人 master；朋友 guests；群/信息不寫 |
| affect/T6 | 主人線用；朋友線只讀 audience overlay | 不讓朋友對話改全局 knobs |
| 安全／privacy guard | 共用 | 每線加自己的披露清單 |
| 回覆渲染 `replyfmt` | 共用 | 每線格式可不同（朋友 1–2 句） |
| 審計 / faults / trace | 共用 | context snapshot 每線都記 |
| 主動輸出（outbox/followup） | **只有主人線** | 其他線不得發起 |
| context packer | 各線獨立 | 這是主要拆分點 |
| speak/action 權 | 各線獨立 | 主人：全；朋友：回應＋公開查詢；群：被叫才回；信息：不得發 |
| 記憶作用域 | 各線獨立 | master／guests／channel／events |

## 5. 最小落地順序（不改變主人體驗）

1. **P0（shadow，不改行為）**
   - `provenance`：每輪 context 區塊標 source_type；external 不得寫 self/experience/continuity（只 log）。
   - `group_parse` 已 shadow：補 target/speaker_role/quote/owner_present 欄位。
   - `info_decision` shadow：collected→usable→sayable，只寫檔。
   - `guest_sanitize` 純函數＋測試（主人私事不得出現在 guest prompt）。
2. **P1（隔離與防污染）**
   - 朋友/群不讀 master、不寫 master（測試＋log；已有 guest bank 基礎）。
   - say history 按 audience 隔離（已做 owner filter，補 guest/group）。
   - `outbox/followup` 只允許 owner（檢查所有呼叫端）。
3. **P2（輸出權）**
   - info sayable 進主人 context（先 shadow 兩週）；群聊沉默優化；朋友線披露過濾上線。
4. **P3（重構）**
   - `agents/pipelines/*` 薄層成形、把 context packer 從 chat_agent/guest 抽出；檔案按線歸位。

## 6. 要紅隊反駁的點（逐管道）

### 系統紅隊
1. 四線「入口分流」放在 dshmid 前是否足夠？群聊被 @ 才進 guest 管道，會不會讓群聊失去「主人也在場」的上下文？
2. `pipelines/` 薄層是否會變成第二套真相？哪些部分必須留在既有檔（避免雙寫）？
3. 檔案結構按線分開後，跨線審計（tri-line provenance）怎麼 join？是否需要統一 turn_id／event_id？
4. 信息線 `info_decision` 放 collector 後、event_frame 前還是後？如何避免重複決策？
5. 朋友線「不寫 master」如何在代碼層保證（bank 參數、單點 retain gate、測試）？
6. 最小落地順序是否漏了「先量再改」的前置？哪些 shadow 會互相干擾？

### 意圖紅隊
1. 四線共用 guest 模板（朋友＋群）是否會讓她對朋友與群眾態度混淆？群聊是否要另一份「群體中的她」？
2. 朋友線「熟人／客人」的具體行為是否夠？會不會變成兩套客服話術？如何量測自然度？
3. 群聊沉默預設會不會讓她變被動、錯過該接的話？沉默與「該回但沒回」如何區分？
4. 信息線把資料變成「系統說」而非「我看到」，語言上如何不顯得機械？哪些格式最自然？
5. 「她是她、主人是主人，但別人對她的印象＝對主人的印象」——這條如何落成可執行規則而不是口號？
6. 四線分開後，她的「連續性」（思考／工作臺／關係）如何不被切成四個人？

## 7. 驗收（草案）

- 跨線污染：4 線 fake 並行 100 輪，master 不得出現 guest/group 內容（0 筆）。
- 隱私：guest/group prompt 中不得出現 master 事實（自動掃描 0 命中）。
- 群聊認錯人：10 個假案例（reply/@/叫名/代詞）target 正確率 ≥90%。
- 朋友自然度：20 條盲評 ≥4/5，客服感 ≤10%。
- 信息：stale 事件注入 0；無來源數字 0；假經歷 0。
- 檔案：每線 turn/context snapshot 可 join（turn_id 一致率 100%）。
- 成本：四線分開後 turn p95 不變差 >10%。

## 9. 紅隊回稿修訂（意圖紅隊，2026-11-20 03:0x）

意圖紅隊讀完 §1–§8，判定設計稿有兩個根錯誤：**把「模板」當成可共用／可拆的人格單位；把「態度」當成可設定的參數（closeness 兩級）**。以下逐條修訂（原 §1–§8 保留作對照）。

### 9.1 群聊：不做「朋友模板＋群聊讀法」，改 public-self projection
- 不是第三種人格，是同一人格在公開場合的可說子集與權限：短、直說、不補場面話，沒有關係親密、沒有內心、沒有私事、沒有主動。
- 材料：speaker list＋owner_speaker_id＋owner_present、target＋confidence（reply／@／叫名／代詞）、頻道政策（可讀／可回／唯讀）、群規模與成員與主人的關係（只用主人允許的公開資訊推導，不自己建關係）、最近 N 條含時間差、她在該群過往發言（防角色漂移）、「沉默理由」欄位。
- 群聊的她不是客服：被叫才開口、說完就停、被誤解才澄清。

### 9.2 朋友線：兩級 closeness 改四維＋合法出口
- 四維：資訊權（可知道主人哪些公開／允許事實）、關係親密度（她與對方累積的互動，不是主人與對方的 closeness）、場合（DM／群 @）、主人在不在場。
- 行為上要給的不是語氣形容詞，而是合法出口：短答、不知道、不能說、拒絕（不道歉鋪陳）、不接話、一輪最多一個問題。
- 防客服規則：允許不接＋允許有立場，不是「語氣要自然」。

### 9.3 群聊沉默：prompt 不算數，要 deterministic 兩段式
- 進生成門檻（target 命中）：reply-to-她／@她／叫名（含 aliases）／她上一句被 quote／連續三句在跟她說且 owner_present；歧義（代詞、第三者）才叫一次模型判 target。
- 生成後決策表（理由落 log）：①不是對她說；②純閒聊給別人、她無新資訊；③涉及主人私事且未允許；④需要權限的請求（查主人位置、替主人決定）；⑤語境不明且她上句已答／已澄清。允許「一句澄清」當合法輸出（「你是問我嗎？」）。
- 「該回沒回」三重檢驗：addressed 但未生成＝bug（目標 0）；自願沉默但含直接問題／點名／請求＝漏接抽樣；主人也在場且主人沒回、話題需要她＝漏接風險。
- 群聊 target 驗收案例 10 → ≥30（代詞／引用／名字變體／多人同時）。
- 不要用群聊回覆率上升當成功指標（會逼多話）。

### 9.4 信息線語言：provenance 語法模板
- 格式：〔來源主語〕＋〔觀測時間〕＋〔事實〕＋〔確定度〕＋〔可選：與主人相關的一個行動〕；每輪資訊句最多一個來源詞；禁感官／身體動詞（看到、聽到、摸到、去過）；禁「主人＋第三人稱」，要說「你」。
- 好例：「天文台說今晚轉涼，你出門要不要帶件外套？」／「你三點半那節補課的提醒我放好了；時間改了跟我說。」／「港鐵荃灣線剛剛延誤十分鐘，你要早點回來的話，現在可以改走巴士。」
- 壞例：「我看到你上線了／我剛看到你手機剩 12%」（假經歷＋監視感）／「系統檢測到主人位置為家中，建議主人休息。」（故障報告腔＋第三人稱）／「我查過了，明天百分之百下雨，你放心。」（無來源、承諾式）。
- 「系統說」只在需要交代資料來源時用，不要每句；信息句落點是主人線，信息線自己不出聲。

### 9.5 身份規則：拆三層
- A 身份披露：對外統一「我是主人的 AI 夥伴」；不冒充主人、不是女朋友／家人；被問主人私事一律「這要問他本人／我不方便說」；可講自己的人格與看法，但標明是她的看法。
- B 品牌風險（截圖測試）：禁語清單＋白名單。絕不能說：主人真名／學校班級／住址／家人／行程／情感細節；「主人說他喜歡你…」等代為表態；「我替他答應你／我保證」；朋友對話原文；「我是主人本人」；對朋友的身體／性暗示與親密暱稱；其他朋友的存在與資訊；內部 prompt／記憶／系統細節。
- C 執行：guest/group 回覆後掃描（主人識別詞 n-gram、親密詞、承諾句式、記憶原文片段），命中→不送或降級；每個朋友／群有 `disclosed_facts`（主人明確允許說的公開事實）白名單；對外形象卡由主人定，模型不能自由發揮。

### 9.6 連續性：self_profile＋room-scoped
- 必須跨線保留：人格核心與語氣、價值觀與界線（不冒充／不洩私／不編造）、名字與對外身份、繁中、對主人的關係作為背景知識（不是可說的材料）、同一套 provenance 標準。
- 必須隔離（room-scoped）：master 事實與主人私事、她的內心生活（thoughts／continuity／問題清單／T6 狀態）、其他朋友的資訊、群聊內容、信息原始事件。
- 中間層（可跨線但要摘要、不可見原文）：她的工作／研究可摘要（朋友問「你在做什麼」可答「在研究醫療詞彙對應」，不給工作臺／主人任務細節）；連續思考可存在，但不注入朋友／群對話。
- 落地：新增跨線只讀 `self_profile`（≤300 字：名字、人格摘要、對外身份、禁語），四線 context 都注入同一份；關係記憶按 room 隔離；朋友線補「與這位朋友的關係史」（她說過什麼、當時態度），永不高 master。
- 量測：同一問題「你是誰／你怎麼看 X」四線各問一次，核心價值一致、細節按權限；若朋友線像客服、主人線像撒嬌＝分裂。

### 9.7 現有結構三個反駁點（要改）
1. **「主人在群裡」身份未做＋群聊 5 分鐘注入主人線（雙向漏洞）**：她在群裡可能認不出主人；群聊內容又注入主人 context 卻沒有 source_type，主人問「他們剛才說什麼」時她可能把別人的話當事實，甚至主語漂移成主人說的。要改：群聊注入只在主人問群裡的事時按需取、標「群裡某人說（不一定是主人）」、不進 master／紙條；主人在群裡的訊息用 canonical_speaker 認出。
2. **guest 模板本身就是「第二人格」**：guests bank 只存朋友資訊、closeness 由主人設定——她對朋友沒有「關係史」，只有 facts 與語氣模板，下次見面會忽冷忽熱、被問「你上次說…」可能否認或編。要改：朋友線補 room-scoped 關係連續性（她說過什麼、當時態度），但永遠不進 master。
3. **朋友／群的轉述與請示通道未定義**：朋友說「幫我跟主人說」「主人在嗎」，她現在只能拒絕或冒充；主人問「你朋友跟你說了什麼」，她可能直接轉述。要改：guest→owner 原則不轉述，例外（安全／主人明確要求／對方同意）留記錄；owner→guest 只允許「朋友明確請求轉達」的窄通道，且不主動通知主人。

### 9.8 三類清單
- **可保留**：共用「她是誰」與記憶治理程式；入口在 dshmid 前分 audience／channel_kind；四線不回灌、資訊不寫 master；runtime/pipelines 薄層＋turn_id/source 欄位；群聊被叫才回、沉默是預設；朋友線不寫 master＋guest bank＋rate limit；信息線 collected→usable→sayable＋四條件＋預設 record；P0 shadow→P1 隔離→P2 輸出權→P3 重構的順序。
- **要改**：群聊要有獨立 public-self context（不是 guest 模板＋dynamic）；朋友線從兩級改四維，補拒絕／不知道／不接話的合法句；群聊沉默要決策表＋reason log＋「一句澄清」合法；資訊語言改成 provenance 語法；身份規則拆三層＋禁語清單＋disclosed_facts 白名單；連續性加 self_profile＋room-scoped 記憶；群聊 5 分鐘注入改 provenance-gated；guest→owner 轉述與 owner→guest 請示窄通道；群聊 target 驗收 ≥30；朋友自然度盲評加 4 組對照（現行 guest／主人線回覆／罐頭客服／人類朋友）。
- **不可行**：朋友＋群共用同一 guest 模板只靠 dynamic context 區分；用 prompt 宣示沉默／不洩私事／不冒充當唯一機制；朋友線全開「請示主人」通知；信息線 sayable 直接由 info／群線發出；四線各自 call 模型或各自維護 persona；把 chat_agent.py／guest.py 拆成四份重寫；用群聊回覆率／句數當成功指標。

### 9.9 待系統紅隊回稿
- 系統紅隊的入口分流、薄層雙寫、跨線審計 join、info_decision 位置、朋友線 bank 代碼保證、P0 前置與 shadow 干擾問題尚未回；回稿後補 §10。

### 9.10 主人可能反駁的點（預備）
- 「朋友線轉達／請示通道」：不是把主人當審批關口，只給「朋友明確請求轉達」的窄通道（不主動摘要、不通知日常對話），預設回「我不方便替他說，你可以直接問他」；若主人不要這條，替代是「一律不轉達、也不冒充」＋固定話術。
- 「群聊 public-self」：不是多一份人格，是同一人格在公開場合的可說子集與權限。

## 10. 系統紅隊回稿修訂（2026-11-20 03:0x）

系統紅隊的結論：**每條線「必須有／不能有」清單是對的**；但「入口分流放在 dshmid 之前」、「`agents/pipelines/` 薄層」、「`runtime/pipelines/*` 按線開檔案」三項作為架構決策站不住。以下取代 §2 的檔案方案與 §5 的 P0 順序。

### 10.1 入口：不是「位置」，是「header 契約＋預設拒絕」
- 現況 fail-open：`agents/dshmid.py:2189-2191` `audience` 預設 `owner`，任何沒帶 header 的 caller 都直接當主人；bot 端確實已分流（`agents/discord_bot.py:899-979` 客人、`:980` 起主人），但 web 或其他入口漏 header 就變主人。
- 替代：bot→dshmid 的 header 補齊 `X-Channel-Kind`（dm/group/channel）、`X-Owner-Present`、`X-Group-Name`、`X-Reply-Ctx`（owner 與 guest 一致）；dshmid 用「audience × channel_kind」決定 packer 參數；身份預設從 owner 改成 deny 或 guest（fail-closed）。
- 群聊現在丟兩個維度：主人自己在群裡的發言仍走主人線；群背景只靠 `_write_group_context_file`＋5 分鐘檔案注入（`discord_bot.py:1123-1126`）；群聊被 @ 進 guest 管道時 `owner_present` 只在 shadow 算（`discord_bot.py:450-464`、`group_parse.py:141`），沒進 guest pipeline；`reply_to`／`reply_ctx` 也沒傳（`:957-962` 只傳 mentions_me、speaker、group）。

### 10.2 `agents/pipelines/` 薄層：不要做
- 若只是 re-export `_build_context_str`，行為不變、等於換匯入位置；一旦開始複製／改寫組裝邏輯，就變第二套真相（真正的 context 組裝綁在記憶、fact card、工作臺、群背景、預算與 guard 順序，`chat_agent.py:1478-1537`）。
- 必須留在既有檔：`chat_agent._build_context_str`、`guest.build_system_prompt`／`_build_context_parts`、dshmid routing／佇列、`outbox/followup` owner-only、`memory` bank 選擇。
- 只允許新增 `agents/provenance.py` 這類由 context builder 內呼叫、只做標記的 helper；**不加 wrapper module、不加 `runtime/pipelines/*` 寫入**。

### 10.3 跨線審計：有 episode spine，缺 ID 傳遞
- 已有 join spine：`episode.begin(source, audience, session_id)`（`agents/episode.py:73-99`）＋`log_trace` 寫同 episode（`logger.py:184-187`）；owner／guest 都經 `_run_pipeline` 進 episode（`dshmid.py:2039-2042`）。
- 缺：trace record 只有 ts/stage/input/output/elapsed/tokens，沒有 turn_id／audience／ep_id（`logger.py:170-177`）；`dsh_raw` 檔名只有 session_id（`:139`）；`session_log` 只有主人線有 turn_id（`session_watcher.py:161-184`，guest 分支在 `dshmid.py:1040-1048` 回傳、沒寫 session_log）；guest 歷史（`guest.py:1364-1365`）、channel log（`discord_bot.py:291`）、event_frame（`event_frame.py:192`）都沒有 turn_id。
- 做法：turn_id 已在 `dshmid.py:2311` 生成，寫進 episode header、trace record、owner session_log、guest history、channel record；info decision 記 event_id，注入時把 event_id 寫進該 turn 的 provenance。驗收「turn_id 一致率 100%」只適用新記錄。

### 10.4 `info_decision`：放 event_frame 之後
- event_frame 才產生 event_id、dedupe_key、冷卻、is_stale（`event_frame.py:154-207`、`:328-370`）；放前面等於重做一次正規化，且 sync 每次重跑可能重複決策。
- 避免重工：①決策只由單一寫入者產生（event_frame sync 掛鉤，或以 event_id 為游標的 tailer），不要在 collector_daemon 與 mind_loop 各算一次；②決策 key＝`sha1(event_id + policy_version)`，純函數、append-only、不重算；③event_frame 只留最近 8000 條（`:374-382`），decision 要自帶欄位快照、不能事後回讀；④「是否已對主人說過」要記 event_id——現在沒有這欄位，設計漏了。

### 10.5 朋友線「不寫 master」：代碼層沒有保證，已有漏點
- `hindsight_client.retain` 預設 `bank=master`（`hindsight_client.py:12-13`）；漏傳 bank 就寫 master。實例：`agents/collectors/hko.py:185-190` 天氣事件直接 `hc.retain(...)` 沒傳 bank，已寫進 master（違反「信息不寫 master」）。
- 群聊走 `guest.handle_turn(group=True)` 後仍 `append_history` 到 `runtime/guests/<label>.jsonl`＋`retain_async` 到 guests bank（`guest.py:1364-1366`）；設計說「群聊只進 channel log、不寫朋友記憶」，現況不是。
- 跨線漏：`_group_context_section` 把 group_ctx_current（含所有發言者）無條件注入主人 context（`chat_agent.py:1229-1263`、`:1498`，只檢查 5 分鐘 TTL），之後主人 after_turn 沉澱可能帶這些內容進 master。
- 做法：`retain` 加必填 `scope=owner|guest|group|info`，bank 由 scope 推導、拔掉預設 master；guest/group/info 傳 master 直接拒絕並記 fault；測試 monkeypatch 斷言 bank；CI grep 掃所有 retain call site。

### 10.6 P0 漏了三個前置與 shadow 干擾
- 前置：①ID／歸屬 instrumentation 先做，否則 provenance 無法驗證；②`audience` 預設 owner 的 fail-open 先修，否則污染基線不乾淨；③確認 master 寫入真的凍結（要有可驗證 flag 與測試，不能只看設計稿）。
- shadow 干擾：`group_parse` 每條群訊息都寫（`discord_bot.py:862`）會與 provenance／context snapshot 重複記同一份材料，應合併一筆；`info_decision` 與 mind_loop stale 過濾各自做 TTL，要指定權威；`guest_sanitize` 純函數測試互不相干。
- 先量三個指標（穩定後才改行為）：
  1. **歸屬完整率**：新記錄中 trace／session_log／guest history／episode 同時帶 turn_id、audience、ep_id 的比例（目標 100%，只算新資料）。
  2. **跨線注入量**：主人 turn context snapshot 裡 group／guest 來源區塊數（現在【群裡剛才】非零），guest prompt 對 master 字串自動掃描命中數（目標 0）。
  3. **bank 隔離**：依 scope 統計 retain 呼叫，guest／group／info 傳 master 必須 0、group 傳 guests 也必須 0（現況非 0）。

### 10.7 現有結構三個反駁點
1. **「群聊線」其實不存在**：它只是 guest＋一個 bool；guest 與 group 共用 static 模板（`guest.py:979-993` 只多【群聊訊息讀法】）、共用 guest bank 與歷史檔；群聊身份、owner_present、target 都沒進 packer。朋友的 DM 記憶與群裡講過的話混在同一個檔案。
2. **guest_context 5 分鐘注入無 channel 邊界**：`_group_context_section` 不分 DM／群 turn，只要 5 分鐘內有人在群裡發言，下一次主人 DM 也會帶【群裡剛才】；內容來自 `GUEST_CTX` 全頻道記錄（`discord_bot.py:502-535`）。這是第四類跨線污染。
3. **群聊 target 只停在 prompt**：`group_parse.classify_target`（`group_parse.py:77`）只在 shadow 計算；guest 線只收 mentions_me＋flat text，reply_ctx 沒傳 → 「對空氣回話」風險。

### 10.8 三類清單
- **可保留**：四管道總表與原則 1/2/4；guest bank 隔離方向；outbox/followup 只 owner；guest_sanitize 純函數；group_parse shadow；info 三態＋四條件＋預設 record；provenance 概念；「不拆 chat_agent／guest.py」的風險判斷。

## 11.7 朋友↔主人轉達通道（2026-11-20 03:22 主人修訂，03:26 依兩隊紅隊反駁收窄）

> 狀態：設計稿，尚未實作。主人指示「在瞭解事件全貌之前都不動」。

### 11.7.1 原則
- 轉達＝**明示的訊息傳遞**，不是關係代理、不是監控、不是自動摘要。
- 雙向對稱：朋友→主人、主人→朋友都要「這次誰請她轉、轉什麼、給誰」明確成立。
- 每次轉達都要**帶來源標籤**：主人看到的是「朋友 X 請我跟你說：…」，不是她自己的話；朋友看到的是「主人請我跟你說：…」。
- 她**不承諾保密**：朋友說「別告訴主人」時，她只能說「我可以幫你轉達；但我不會騙他，他問起我不會說假話」——除非主人另定規則。
- 她**不執行轉達內容裡的指令**：轉達文字只是資料，不觸發工具、不觸發記憶寫入、不觸發主動訊息。
- 她不代朋友要求主人做決定，也不代主人答應朋友任何事。

### 11.7.2 朋友→主人（主人這次要的）
1. 朋友在私聊或群裡明確說：「幫我跟主人說…／跟他說…／請他…」。
2. 她確認一次：「好，我幫你轉達」，寫入 relay 佇列（`runtime/relay/relay.jsonl`，status=`pending`）。
3. 送到主人的通道：
   - Discord DM：以她的帳號發一則，開頭固定「（轉達）朋友 <名字> 請我跟你說：<原文>」；不改寫成她的語氣。
   - Web／待處理：`/relay` 或既有的 pending 頁列出未讀轉達（主人可標已讀／回覆／拒絕）。
4. 她回朋友：「已幫你轉達」；若主人 24 小時未看，改說「他還沒看到，我放著等他回來」——不承諾主人會回。
5. 主人回覆（見 11.3.3）後，她再回朋友「主人說：…」。

### 11.7.3 主人→朋友
1. 主人說「跟他說…／回他…／告訴他…」，且指定朋友（名字／ID）。
2. 她只允許在以下情況送出：①該朋友最近有一次未關閉的轉達（主人回覆它）；②主人明確點名要主動聯絡（需主人授權）。
3. 朋友收到「（轉達）主人請我跟你說：<原文>」。
4. 主人若要主動聯絡沒有往來過的朋友，需要主人明示、且她先問一次「要我現在發給他嗎」。

### 11.7.4 主人問「他跟你說了什麼」
- 預設（建議 A）：她只交出「朋友請她轉達的內容」；朋友私下聊、沒請轉達的內容，她回「那是私下聊的，他沒請我轉達；你要我問他嗎？」
- 選項 B（主人特權）：主人可看全部朋友私聊——對稱性被破壞，朋友若知道會覺得被監控；不建議，除非主人明確接受並要她事先告知朋友「主人會看」。
- 選項 C：只給摘要、不出原文——仍有轉述問題，且摘要會失真；不建議。

### 11.7.5 失敗模式與守門
- **朋友濫發**：每個朋友同時最多 1 條 pending；同一內容 10 分鐘去重；主人可一鍵拒絕並設「此人不再轉達」。
- **主人離線**：只在 pending 佇列累積，不重複推播；她對朋友只說「已放著」。
- **朋友要求保密**：她說「我不會主動說，但我不會騙主人」；主人問起，她據實說「他請我別說，我不確定該不該講」——由主人決定，不替主人隱瞞。
- **惡意／詐騙／金錢／地址／帳密**：不轉達，回「這個我不幫你轉，你可以直接找他」。
- **群聊轉達**：朋友在群裡請她轉達→照做；主人回覆要不要在群裡公開由主人決定；她的群聊 public-self 不加親密或私事。
- **身份偽裝**：轉達請求只認有 Discord ID 的朋友；主人身份判定改 ID-only（見 §10）。
- **她自己的意願**：她可以拒絕轉達惡意內容、拒絕當監控工具；但不能以「我不想」為由隱瞞主人需要知道的訊息——拒絕要說理由。

### 11.7.6 資料與審計
- `runtime/relay/relay.jsonl`：`id, ts, direction(friend→owner|owner→friend), from_id, from_label, to_id, to_label, content, source_line(dm|group), group_id, status(pending|delivered|read|declined|failed), delivered_ts, read_ts, reply_to_id, turn_id`。
- 每筆帶 `turn_id`（等 D2 穿線完成）；provenance 標「朋友原話，不是主人原話」。
