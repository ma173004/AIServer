## 1. 記憶架構：結論 vs 現況

**現況（可跑）**
- 寫入：`agents/memory.py:159 remember_rounds`（歸檔時批次抽取）；`:240 should_remember_now / :249 remember_now`（本輪值得記就即時記）；`:403 remember_guest_round`（訪客 bank）。
- 存儲：Hindsight banks（master/guests/archive）；runtime/episodes/*.jsonl（每輪全記錄）；runtime/archives/*.jsonl（session 歸檔）；agents/logs/trace、chat_records。
- 召回：`memory.py:326 recall_memories` → Hindsight recall（多 query）→ `_relevant` 過濾 → Memory Worth 雙閘門（`memory_worth.score` <0.35 且 >30 天跳過）→ MAX_ITEMS 條格式化文本。
- 短期：`session_watcher.get_context()`＝summary（1 段）＋最近 8 條；`self_memory`：mind（短期自述）＋workbench（跨回合項目板）。

**對照我的結論**
- ❌「語義記憶/情景記憶/每日筆記三個檔案層」——**映射到既有元件即可**：
  - 語義記憶＝Hindsight facts/observations（master bank）；
  - 情景記憶＝episode JSONL＋歸檔摘要（可尋址句柄在 episode id）；
  - 工作記憶＝workbench＋mind；
  - 短期＝session summary＋最近對話。
- ✅ 真正缺口（細節）：①寫入入口分散（remember_now / remember_rounds / observe_mood 各寫各的，無統一 gateway、無寫入前去重/墓碑/衝突判定）；②召回有去重，寫入側沒有；③長度上限只在召回層（MAX_ITEMS），寫入側無量測/超限拒寫；④可尋址性：episode id 在，但召回文本不帶句柄（worth 閘門需要 id 才有效）。
- 結論：**不做新層，改做細節**——統一寫入入口＋去重/墓碑 hook＋長度量測。

## 3. 上下文注入架構：結論 vs 現況

**現況（`chat_agent._build_system_prompt`／`_build_context_str`）**
- system prompt＝persona（靜態，`tpl.format` 用固定佔位）＋契約（靜態：底線/輸出格式/查資料/下一步）＋ scene block（依場景變）＋ T6 overlay（依狀態變）。
- user message＝【当前状态】（時間、情緒）→【提示】→【历史摘要】→【最近对话】（8 條）→【自我观察】（重複短語）→【历史记忆】→ 工作臺（插在【当前输入】前）→【当前输入】（只放主人原話）。
- 另有 `05_chat_prompt` trace 記錄最終 system/context（/inputs 可看）。

**對照我的結論**
- ✅ 前綴穩定設計基本正確：persona＋contract 是靜態前綴；時間/情緒本來就在 user message。
- ❌ 我高估的問題：「場景/時間/狀態在 system 每輪變」——實際只有 scene/overlay 在尾端變（scene 對主人日常多半是 S1 不變），對 KV 影響有限；「注入順序沒按穩定前綴」也不準確。
- ⚠️ 實打實的兩處偏差（不是架構，是沒改）：
  1. 契約仍寫「回覆像平常說話一樣，順著他的話說你想說的，不用刻意簡短」——主人已否定「平常說話/順著他」且指出我沒理解「不刻意簡短」，我當時說收回，代碼沒動；

- 可選細節優化：把 scene/overlay 移到 user message 讓 system 完全靜態（需 A/B 測收益，先不急）。
