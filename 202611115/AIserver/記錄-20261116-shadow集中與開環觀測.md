## 新增：open loop（開環）shadow

`scripts/shadow_openloops.py`：她問出口、主人還沒回答的問題。

- 來源：`runtime/outbox/sent.jsonl`（她真的送出的 thought/proactive，audience=owner）＋
  `runtime/guest_ctx/channel-*.jsonl`（主人 DM）＋`runtime/archives/*.jsonl`（role=user，含 `reply_to`）。
- 只收真正的問句（`？`／`吗`／`呢`／`吧` 結尾）。care/share 不當開環。
- 狀態四種：
  - `strong_closed`：主人引用她那一句回覆（`reply_to` 對得上）→ 強閉合。
  - `weak_closed`：主人之後有說話但沒引用 → 弱訊號，只算「可能接上了」，不算答案。
  - `open`：48 小時內沒有任何主人訊息。
  - `expired`：超過 48 小時仍沒有回應。
- 輸出：`runtime/shadow/open_loops.jsonl`＋`open_loops_summary.json`（counts／今日／p50 閉合延遲）。
- cron：每 30 分鐘跑一次（`*/30`），只寫檔。
- **不進 prompt**：她目前仍不知道這些開環。

第一次跑（14 天回溯）的結果：2 條問句、2 條 `weak_closed`、0 open。
其中一條正是 23:54 after_turn 的「你說『不會的』時，語氣裡有種對未來不確定的擔憂…」，
主人在 23:55 有說話但沒有引用（weak）。這說明兩件事：

1. 她主動問主人的次數比想像少（多數是 care/share），所以開環資料量小是正常的，不是採集壞了。
2. 弱閉合很容易誤判：主人只是接著講自己的話，也被算成「接上了」。所以 README 明寫 weak 不能當作
   「已回答」，之後若真的要讓她知道開環，只能採 strong（引用）或她自己的判斷。

### 順手修掉的一個真 bug

第一版用 `sent_at`（所有通道含 Web 補送完成的時間）當開環時間，會把開環推遲到主人回覆之後，
造成假 open。改成 `created_at`（她決定說的那一刻）。修完 23:54 那條從 open 變 weak_closed。
