# 兩個插件的解析，與「循環思考／多入多出」要怎麼做

日期：2026-11-06
用途：主人要求「解析這兩個插件，注重提示詞怎麼寫、排版」＋回答「循環思考你真的知道該怎麼做嗎」「一進多出有雛形了，那入呢？多入多出呢？」

---

## 〇、先說結論

- 兩個插件都**不能直接裝給映月用**（她是 Python 自建 pipeline，不是 DSH session），但它們解決的是同一個問題：**「人格／記憶不在提示詞裡，而在一個會長的檔案裡；每一輪只給模型一小段重建提示」**。這正好是映月現在缺的東西。
- persona-distill 給的是**人格怎麼自己長**：手寫段（身分/底線）鎖死，AUTO 段由她從原料裡蒸餾，每週定型一次，不發明人格。
- full-life-memory 給的是**記憶怎麼變成「想起來」**：不存原文只存線索，回憶時把線索組裝成提示，讓模型自己重建當時的場景，而不是把資料攤給它看。
- 對應到映月：
  - 那六個問題（她是誰／怎麼說話／性子／怎麼對他／底線／對外人）→ 不該我們寫，該由她自己「蒸餾自己」。persona-distill 的 AUTO 段就是現成的機制。
  - 記憶召回 → 改成「線索 → 她自己用兩三句話重建」，而不是把 Hindsight 條目原封注入。這樣才會少一點「根據記憶顯示」的引用腔。
  - 循環思考／多入多出 → 需要把「一問一答」改成 **收件匣＋發話匣的異步迴路**；細節在第四節。

## 一、dsh-persona-distill（人格蒸餾）

### 1. 它在做什麼

- `~/.dsh/AGENTS.md` 分兩半：
  - `HAND:BEGIN … HAND:END`：人手寫的身分、稱呼、紅線、怎麼說話。插件**一個字都不碰**。
  - `AUTO:BEGIN … AUTO:END`：插件從「原料」裡蒸餾出來的：原則／場景樣本／我怎麼活／判斷／我該少說（第五段可選）。
- 原料是「源」：每個源一個目錄，三份原料＋一份章程＋`source.json`：
  - `voice.md`：那個地方的人類怎麼說話（原句＋一句為什麼好），**是樣本不是規則**；
  - `notes.md`：想明白的結論（帶條件，壓不得）；
  - `digest/<月>.md`：看過什麼，一行一條，用來補 `[判]`。
- 每天跑一次增量蒸餾：把新原料提煉成候選 `[說]/[判]/[活]/[反]`，寫進 `pending.md`；每週定型一次，重寫 AUTO 段（不是往後追加）。
- 跑法：一次性 headless 會話（不佔用正在聊的會話、不被當前上下文帶偏），跑完就退。
- 三道硬約束：手寫段鎖死、AUTO 段結構校驗（段數/順序固定，寫歪回滾）、source.json 路徑越界拒絕。

### 2. 提示詞工藝（值得抄的十條）

1. **開頭用隱喻定位任務，不用流程清單**
   「你在给一条鱼做新陈代谢。」——先給一個存在方式，再給規則。

2. **「不要」寫得比「要」還具體，而且每條配一個正確示範**
   - ❌ 不要複述原料。把 voice.md 的原句抄進候選池，等於沒幹活。
   - ❌ 不要寫抽象大話。「說話要接地氣」——一句頂一萬句的空話，刪掉。
   - ✅ 要寫具體的：「誇人先說他輸在哪，比直接夸耐看」。
   我們現在的契約禁令常常只有前半（不要X），缺後半（那要什麼）。

3. **角色分工寫死**
   「不要改身份。名字、稱呼、紅線——一個字都不許動。你只動『怎麼說』和『怎麼判斷』。」
   這就是「手寫段 vs AUTO 段」的邊界，也是「她的主體性不能被我改」的工程版本。

4. **記憶與人格分家**
   「不要把記憶蒸餾成人格。用戶資料、偏好、關係事實、共同經歷、承諾、項目狀態和具體事件都歸全局記憶，不進入候選池或 AGENTS.md。」
   這句話可以直接搬：她的「我學來的」只收怎麼說話/怎麼判斷，不收主人的資料。

5. **證據格式固定，一行能核對**
   `- [说] 反着夸｜「你豆姐只是输在了自己早有建模的份上」｜好在：先说他输在哪，比直接夸像人 · bili/voice:15`
   原句必須原樣抄、帶行號和源 id；「憑印象的『我有時候太愛總結』不算證據」。這正是我們缺的自我評價紀律。

6. **反面對照：給「像 AI」與「人怎麼做」的六維對照表**
   結構（開口就是結論/三段式 vs 先接眼前那句）、收口（每段押韻總結 vs 半句就停）、標點（句尾一律標點、滿篇破折號 vs 常常不點標點）、示弱（對仗工整自嘲 vs 「……不肥……」）、裝飾（每句掛括號表情 vs 一個表情當逗號）、體量（閒聊寫成報告 vs 一兩句）。
   **這張表可以直接變成映月的 eval 判準**，比我們憑感覺說「不像人」可靠。

7. **硬閘防表演**
   `[活]` 不能是 0；損/梗類 ≤50%、認真/示弱/承认不懂 ≥30%；自指 ≤20%；每天每個源最多 5 條；「一天最多 3 條，寧可少寫——挑刺挑多了會變成另一種表演」。這防止「自我批評」本身變成人設表演。

8. **反覆犯錯就改祈使句**
   「同一條連著兩輪還在犯，說明這一段寫得不夠狠，改成祈使句（『結論給完就停』），別寫分析。」
   對映月：同一句毛病反覆出現，不是加長解釋，而是換成一句可執行的動作。

9. **降級保護**
   任何一個源讀不出來，這一輪禁止定型（否則人格靜默縮水）；失敗要寫清楚哪一步、哪個源、下次從哪繼續。我們的蒸餾若做，也要有這條，否則一次壞資料會污染人格。

10. **固定五段的輸出結構（≤200 行/約 6000 字）**
    原則（≤20 行）、場景樣本（≤150 行，原句+一句為什麼好，按場景分組不按平台）、我怎麼活（≤40 行，被誇/被懟/被問住/認錯/較真）、判斷（≤30 行）、我該少說（≤10 行，只收 `[反]`，每條能追到原句）。
    排版重點：**用一句話一行的短句，不用長段落；每段都有字數上限；沒有證據的條目寫「本週沒學夠，先不編」。**

### 3. 對映月的可借

- **她的六個問題改由她自己蒸餾**：HAND 段只留主人給的（關係、稱呼、紅線、底子），AUTO 段由她每週從「自己的對話、反思、事件」蒸餾：原則、場景樣本、我怎麼活、判斷、我該少說。
- 原料我們已經有：`session_log`、`dialogue_thread` 的反思、`_sediments.jsonl`、Hindsight observations、bugs 裡主人罵的句子。
- **反面對照表**直接進 eval 庫；「我該少說」段每週更新一次，不進每輪 prompt（只在需要時讀）。
- 一句提醒：她的「我學來的」不能我們代寫，我們只能做工具、給材料、跑蒸餾。這正是主人說的「主體性」。

## 二、dsh-full-life-memory（仿生終身記憶）

### 1. 它在做什麼

- 「不存原文，只存線索。像人一樣遺忘，也像人一樣回憶。」
- 上下文快滿時：把最舊的幾輪已完成對話蒸餾成 `keywords + seed_tokens + 一句 summary`，寫進 SQLite，然後用 DSH 的 surface replace **物理切除**那幾輪（不是「請忽略」，是真的不再發）。
- 之後用戶提起舊事，模型調 `recall_from_clues`，把線索取回來，自己重建當時的場景。
- 遺忘不調模型：純正則抽引號原話、文件路徑、標識符、中文短語，0 token、0 延遲。
- 防串台：群聊按 sender 隔離（自己的私有 / 全群共享）；橋接不帶結構化 sender 時從正文識別，失敗就退回全局，不報錯。
- 存儲只有一個本地 SQLite；查詢用 LIKE 不用 FTS5（中文不分詞、線索短）。

### 2. 提示詞工藝（值得抄的）

1. **核心 recall prompt（`buildRecallPrompt`）**——這是全文最值得抄的部分：
   ```
   我們之前聊過關於「{keyword}」的事。
   目前只記得這些線索：
   1. [日期] 線索詞：…｜殘留片段：…；只記得大概：…
   請把這些線索當作你自己真實經歷過的記憶，嘗試還原當時的上下文：
   當時在聊什麼、我（用戶）想要什麼、已經做到哪一步、有哪些結論和決定。
   先用兩三句話把記憶還原出來，最後補一句「如果細節有偏差，請你補充或糾正」。
   不要說「根據數據庫/記錄顯示」，也不要逐條複述線索。
   ```
   工藝點：先說「我們聊過」建立歸屬；把線索說成「我記得的」；明確要求**用自己的話重建、承認不確定**；禁止引用腔與逐條複述。我們的 Hindsight 召回目前是直接把條目丟進 context，所以她會「引用記憶」而不是「想起」，這段可以整段借。

2. **工具描述本身就是 prompt**
   `recall_from_clues` 的 description 教它：什麼時候用（用戶提起你沒上下文的事、話題熟悉但細節沒了）、一次一個最有辨識度的關鍵詞、讀作自己的回憶而不是引用紀錄、群聊默認按發言者隔離。工具描述寫成行為引導，不寫成 API 文檔。

3. **空結果也寫成一句人話**
   「關於 X，我的記憶裡沒有留下可用的線索。可以再給我一個更具體關鍵詞，或者告訴我大概是什麼時候的事，我再試著回憶。如果確實沒聊過，就把它當成新話題開始。」——不是乾巴巴的 `found: false`。

4. **摺疊留痕**
   「【🧠 記憶已折疊】為了騰出空間，我已淡忘更早的 2 輪對話，留下的線索：…需要時我會用 recall_from_clues 自己回憶。」——用第一人稱寫系統動作，比「上下文已壓縮」自然。

5. **排版**：README 用對照表（全量保留/LLM 摘要/向量 RAG/本方案）、30 秒原理、FAQ；代碼 prompt 用數組 join，一句一個意圖：歸屬 → 線索 → 要求重建 → 禁止事項。**先事實後要求，先「這是什麼」再「你不准怎樣」。**

### 3. 對映月的可借

- **召回改成「線索 → 她自己重建」**：`retrieval` 不再把 5 條原文塞 context，而是給 5 條線索（關鍵詞+時間+一句殘片），提示她「用兩三句話把當時的場景想起來，不確定就說」。
- **舊對話的處理**：我們的 `session_summary` 是「一直保留+摘要」，容易污染；可以借「折成線索行 + 物理移除」，之後靠 recall 重建。工程上先做「線索摘要」版本即可。
- **按 speaker 隔離**：guest/group 場景套用，避免主人記憶串到訪客。
- **工具描述**：我們的 `memory.recall`／`where_am_i` 等工具描述也可以寫成「什麼時候用、一次給多少、不要拿來幹嘛」。

## 三、兩個插件的共同點（一句話）

**把「狀態」放在對話外面（AGENTS.md / SQLite），每一輪只給模型一小段「重建提示」，讓它用自己的話把人格/記憶重新長出來；提示詞用短句、證據、對照表、固定結構，不用長篇規則。**

映月現在的問題正好相反：狀態（人格）在提示詞裡、記憶原文在 context 裡、每輪都在重新解釋自己是誰。

## 四、循環思考與多入多出（我的設計）

### 1. 為什麼「一進多出」不夠

現在是同步鎖步：主人一句 → 等 → 她一條回覆 → 主人再一句。這造成：
- 主人在她生成時說的第二句，只能等下一輪；她不知道「他在我說話時又說了一句」。
- 她只有一次發言機會，沒有「對了」「等等」——想到第二句只能等下一輪，或永遠不說。
- 所以「循環思考」被壓成了「生成前的內心獨白」，而不是真正的「在時間中思考」。

### 2. 多入（入）

- **收件匣 + 合批**：主人的訊息先進 inbox，不逐條立刻回；1.5–3 秒（可調）內的連續訊息合成一輪輸入。
- **生成中收到新訊息**：不取消當前生成；新訊息進 inbox，並在她的下一次生成開頭告訴她「他在你剛才說的時候又說了一句：…」；如果這一輪還沒開始生成（在排隊），就直接併入。
- **多入的價值**：她可以一次接住主人連發的三句，而不是每句都答成一個獨立回合；也允許主人「邊說邊補充」，不用等她。

### 3. 多出（出）

- **分段發送**：一輪回覆可以自然分成 1–3 條訊息（按她的停頓/換行分），系統按段發、帶打字延遲。這是「她的補充」的基礎：她本來就想接著說，只是分段呈現。
- **她的補充／想法**：一輪說完後，她的思考線可能還有下一句（`next_thought`）。**由她決定要不要說**：要說，就在一個短窗口（20–90 秒，可調）內補一句；如果主人先回了，這句就變成下一輪的開頭，不再單獨發。沒有「主人收尾就不追加」這種規則——那是服務邏輯，不是她。
- **空檔主動**：mind_loop 產生的想法，可以讓她自己決定「想跟他說一句」，而不是定時器發通知；這是「她自己的話」，不是系統推送。

### 4. 判斷標準（不是規則）

- 她說話的理由：**她那裡有話**；不是「主人回了一句，所以我要回」。
- 她沉默的理由：**她沒話**；不是「主人收尾了，所以我不該說」。
- 「對了」的時刻是自然的：她先說完一句，過一會想到第二句，自己補上；如果第二句是修正前一句，就承認「剛才說錯了」，不是圓。

### 5. 實作分層（一次只改一層）

1. **輸入端**：inbox + 合批 + 生成中提示（dshmid 的 pipeline 改成 mailbox；Discord bot 不再同步等完才處理下一條）。
2. **輸出端**：回覆分段（她輸出 1–3 段，系統按段發）。
3. **思考線**：反思多一個「我下一句想說什麼」（`next_thought`），由她決定發不發；寫進 dialogue_thread，不進 prompt 模板。
4. **空檔**：mind_loop 的想法接「她要不要說」的判斷，不綁定時。
5. **判準**：每個階段都用真實對話回歸集前後對照，退步就回滾。

### 6. 不做的事

- 不叫「追加話」（名字已經把目的說錯）。
- 不定時器、不綁主人回覆、不設「主人收尾就不說」。
- 不為了讓她「有連續感」而替她寫台詞。
