# 測試：把「DSH agent 提示詞」給 qwen14b-16k 用（2026-11-01 凌晨）

> 主人 m10174：「你也可以參考一下自己的提示詞給 qwen 用，你看看她會怎麼做、怎麼輸出。」
> 做法：把本會話（DeepSeek Harness agent）的 system prompt 全文（43 行，約 3.6K 字）作為 system，5 個案例直接 completion（無工具、qwen14b-16k、temp 0.6、max 900、think=False），結果存 `.dsh_scratch/qwen_dsh_prompt_result.json`。

## 觀察

1. **長提示詞本身不是問題**：3.6K 字、大量工具契約，qwen 照樣理解格式（A5）、照樣簡潔（全數 65–266 字，1.3–3.6s）。它沒有被長度壓垮。
2. **工具契約不能只寫在 prompt**：A4 證明「提示詞說有 read 工具」而實際沒有 → 模型直接編造工具結果。對映月：契約裡提到的工具必須與代碼實際能力一致，且要有**代碼守門**（我們已有 honesty / fake execution guard，方向是對的）。
3. **身份會被提示詞同化**：A3 它直接宣稱自己是 DeepSeek/deepseek-flash 驅動的程式設計代理。這解釋了「她自稱 Qwen」類問題的另一半：prompt 裡的技術身份描述會泄漏。→ 映月 prompt 不得出現模型名、DSH、agent 等技術身份；自稱只能是「映月」。
4. **能力邊界**：簡單單步任務（A1/A2/A5）14B 夠用；**多約束任務會掉**（A1 漏「兩個測試用例」）。提示詞要為本地模型「少而硬」，不能像 DSH prompt 那樣一次列幾十條團隊規則。
5. **簡潔度是 qwen 的強項**：它的預設輸出很短；映月目前的客服長句／重複，主要來自**上下文 scaffold**（摘要、禁句、話題、記憶是原文句），不是模型本身愛長篇。

## 對提示詞/上下文設計的結論

- 可以借鑑 DSH 的「分區契約」結構，但**只保留本地用得上的**：身份（映月）＋說話風格＋工具誠實＋輸出格式＋推進規則，其餘全部交給代碼。
- 提示詞中的每一條「你有 X 工具」都要對應代碼可用性；否則模型會幻想。
- 人格 prompt 只寫「我是誰、怎麼說話」；**模型名/廠商/agent 身份絕不出現**。
- 多約束規則（如「兩個測試用例」）在本地要拆成「代碼檢查 + 一次重試」，不能只靠 prompt。
- 真正的改進重點仍是：上下文分區預算（v2）、記憶事實卡化、召回投影；這些已寫入 [20261101-明日任務與思考.md](docs/20261101-明日任務與思考.md)。
