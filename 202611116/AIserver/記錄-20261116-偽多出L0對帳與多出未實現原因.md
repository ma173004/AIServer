## 三、多輸出為什麼沒有實現（事實更正）

`docs/設計-20261107-多入多出與回合佇列.md` 當時定的是：

- `:32`「回合內分段輸出：一次生成可切多個氣泡」——**從未實作**。
- `:34-51`「回覆後立刻再想一次，有話就第二個氣泡，<skip> 就停」——這就是 after_turn 原型；實作後內容多為研究／meta 重複，11-15 主人叫停。
- `:90-99` 多條 outbox 訊息、多來源 inbound——這些是「多條獨立訊息＋多通道」，不是「同一輪多氣泡」。

真正落地的：多來源 inbound、MIMO 合併、回合佇列、outbox、followup。Discord 一直是單則回覆；「一次生成切多氣泡」從未開始。因此：
- 不是「做了多輸出但沒生效」，是**只做了多輸入與多通道**。
- 我上次說「一請求一回覆是協議層事實」也不完整：MIMO 會把多則合併成一個請求，followup 另有第二條通道。
- 「多輸出」的正確落點是**同一則回覆內的分段／多氣泡**，不是背景第二條訊息，更不是共用事件流。

## 四、兩隊紅隊的反駁（2026-11-16 晚，第二輪）

兩隊一致：
- **不做三層事件流、不做統一 agent/queue**。
- **不做 proposal→policy**（系統紅隊：只是把 gate 搬進 outbox、變成不可見的守門；意圖紅隊：policy 決定發＝腳本控制主動訊息，違反主人「主動信息由她自己決定」的原則；會讓她學會寫 proposal 給人看、變得不敢說）。
- **先做嚴格 L0 對帳**（已完成，見上），再決定是否修生成與通道。
- 真正成本不是磁碟，是「以為做了」：事件 id 會讓記錄更像行動、讓重複合法化。

失敗案例要點（兩隊共 20+ 條，摘錄）：
- event id 讓同一句在三個帳本各掛一個 child，看起來像三次輸出。
- delivery 沒有 ack（outbox 只有 queued/web_ts；Discord message_id 只在 bot DM history；Web 無 ack）→ 無法證明送出。
- replay 非冪等（工具、記憶、發送都是 side effect）。
- 崩潰半寫、多 writer RMW、audience 隱私混線、時序錯置、歷史無法回填。
- proposal/policy 會誤殺 care/share/invite 與「沒事想到你」；研究類反而最容易被 evidence_ref 洗白。

## 五、修正後的最小路徑（待主人拍板，先不改行為）

1. **L0 每日對帳**（已完成第一版）：固定 outbound＝outbox 實際 emit ＋ chat reply；decision/shadow/thought 只算候選。每日輸出三張表：日誌重複、送達重複、語義重複。

5. **真正多出不納入本週**：若要做，先做「同一則回覆內分段」，不是背景第二條。
