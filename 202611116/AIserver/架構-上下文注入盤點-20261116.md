## 0. 一回合的總覽

owner 一輪（DM 或群裡叫到她）：

```
system = 人格模板(persona) + 契約(_contract) + 場景 overlay(scene) + T6 overlay(當前行為約束)
user   = 【時間與場景】…【當前輸入】（見 §2，總預算 2000）
user 包裝 = 用户原话：<原話> + 【前置任务的结果】/【動態創建（可選）】/【依賴任務】…
模型   = claude16k（native think）
輸出   = reply（→ dshmid 清理→繁中→回覆）
```

guest 一輪（朋友）：

```
system = GUEST_TEMPLATE + 客人契約（不含 owner 契約）
user   = 【群組／頻道最近消息】/【最近對話】/【客人現在說】+ guests bank 記憶
輸出   = guest 話術（「您」、短、只答不問）
```

四條管道在程式裡目前**不是四條**，而是兩條 audience（owner / guest）＋一條旁路（collector 資訊，幾乎不進 chat）＋群聊背景（只影響 owner 群）。這就是「不存在 group audience」的現況：owner 群 = owner audience + `group=True`；guest 群 = guest audience + `group=True`。

### 分層原則（為什麼要分這四層）

- **system＝她是誰、怎麼說話**：每輪固定，前綴可緩存；人格與契約不隨對話內容漂移。
- **user context＝她這一刻知道什麼**：每輪動態、可裁剪；時間、資料、記憶、對話、他人狀態都在這。
- **user message 包裝＝這一輪的任務邊界**：哪些是主人原話、哪些是系統給的附件/前置結果/動態子任務；防止把系統字串當成主人說的。
- **guest 管道＝她對朋友是誰、能說什麼**：與 owner 完全隔離，避免主人隱私外洩，也避免用主人線的人格/記憶接待朋友。

## 4. 預算與裁剪順序（超 2000 時）

依 `_build_context_str`：摘要 → 群聊背景 → 等待問題 → 提醒 → profile hint → 歷史記憶 → 工作臺 → 我此刻 → weather → judge → 最舊對話 → outbox → inbound → thread。**當前輸入永遠保留。** 最後 `abstract_refs.compact_text` 把 URL 變 [連結N]、已知路徑變【別名】。

system 端：base（人格＋契約）先截，場景/T6 overlay 最後 append 且優先保留。

**為什麼要有裁剪順序**：user context 的內容會超過 2000；先砍最不影響本輪理解、最可重建或最容易過期的（摘要、舊群背景、等待問題），保留當前輸入與近期對話，避免「因為塞太多而把主人剛說的擠掉」。

## 7. 現況問題（盤點結論）

1. **兩條 audience 假裝四條管道**：owner/guest 之外，資訊與群信息沒有自己的注入協議；group 只是 owner/guest 上的一個 flag。
2. **群聊只有「文字背景」**：U-12 是一段格式化文字，沒有 speaker_id/canonical、target、is_owner、owner_present；被叫與否的判定在 bot，chat 看不到。
3. **朋友的上下文與主人完全不共享**：好處是零洩漏，壞處是朋友線無法承接主人提過的關係（她自己也不知道「這個朋友是誰」的結構化資料，只有一句 relation）。
4. **資訊線幾乎沒有消費層**：collector 資料都在，但沒有「事件→意義→可用度→輸出/記錄」；舊模板 proactive 已 retired，所以現在只剩工具查詢與 U-8 天氣預取。
5. **T6 只作用 owner 線**：guest 沒有 affect；朋友線的 AVP/防備目前沒有入口（放在技能待 T345 穩定）。
6. **主人專屬塊太多且每輪全塞**：工作臺、事實卡、摘要、記憶、主人快照、我此刻、提醒、profile hint 同時進 2000 字；彼此重疊與噪音已在審計中看到（工作臺 8% 使用率、摘要十四歲錯字）。
7. **沒有 provenance**：每個注入塊沒有 source/valid_from/valid_until/confidence；錯了只能靠人抓。
8. **群聊背景 5 分鐘有效但只存最後一個頻道**（`group_ctx_current.json` 單檔覆寫），多群並行會互相蓋掉。
9. **guest 群與 owner 群共用 `runtime/guest_ctx` 目錄與 channel 檔**，audience 不同但落盤混在一起，之後做群解析要小心。
10. **思考/經驗/連續性不進對話**：她能想但看不到自己的思考史；聊天端只有【我正在想】一句摘要。

## 8. 四管道分流矩陣（初步提案，待主人拍板）

> 定義原則：**管道 = 「對誰說話、能拿到什麼資料、能動用什麼工具、輸出到哪裡」**；人格與安全是共用層，不是管道。

| 維度 | A. 我（主人 DM/私聊） | B. 朋友（guest DM） | C. 資訊（collector/event） | D. 群信息（Discord 群） |
|---|---|---|---|---|
| audience | owner | guest | 非對話（資料流） | owner 群→owner＋group；guest 群→guest＋group |
| 人格/契約 | owner persona v9＋owner 契約 | guest 模板＋guest 契約 | 不適用 | owner 群用 owner；guest 群用 guest |
| 場景 | S1 私聊/S2 任務/S5 主動（未開）/S6 沉默 | S3 私聊 | — | S4 群聊/S6 沉默（owner）；S4（guest） |
| T6 | 全通道（overlay＋energy＋行動傾向） | 只做「態度向量」（慢變量），不做全身激素 | — | 沿用對話對象的 T6（owner 群 owner 線） |
| 主人資料 | 全部：快照/工作臺/事實卡/摘要/記憶/提醒/我此刻 | **不可見**（只給關係卡：稱呼、關係、偏好、最近互動摘要） | 只給與主人相關的事件（去識別化） | owner 群可見主人相關；guest 群不可見 |
| 記憶 bank | master＋archive＋mirror | guests | 無（事件存 event_frame/collect） | owner 群→master；guest 群→guests |
| 對話歷史 | session_log（owner） | guest session | — | owner 群 session；guest 群 guest session |
| 工具 | 全開（safety 白名單） | ALLOWED_TOOLS（受限） | 只讀快照/正規化，無對話工具 | 同 audience 工具，但群聊預設沉默 |
| 輸出 | Discord DM/Web/主動訊息 | guest 回覆 | 不直接輸出；供 A/D 查詢或主動訊息素材 | 群裡回覆（被叫才回）；不主動 @ |
| 預算建議 | user 2000（現況） | user ~800–1000 | 0（不進 chat）；進 A/D 時以「事件卡」≤300 | user 1200–1500（含群背景≤400、被叫句、speaker/target） |

### 8.1 各管道應注入清單（提案）

**A. 我**
- 保留：人格、owner 契約、S1/S2、T6 overlay、時間與場景、主人情緒、reply_ctx、主人此刻、我此刻、上次對話、judge（中性化後）、天氣（問到才給）、事實卡（按需投影）、工作臺（只在相關回合/有變動時）、摘要（history<4）、對話、提示、歷史記憶（相關才給）、提醒（有 pending）、outbox/inbound、thread、當前輸入。
- 調整：事實卡只按本輪投影；工作臺按需注入；摘要只留主人原話；記憶加 provenance；提醒按時間窗（只給 24h 內＋最近一件）。
- 不該：collector raw items、群聊背景（DM 時）、guest 資料。

**B. 朋友**
- 注入：guest 人格＋契約、S3、關係卡（誰、怎麼認識、主人怎麼稱呼他、距離/態度、最近互動）、guests bank 記憶、guest session 歷史、頻道背景（如果是群）、當前輸入。
- 不注入：master 記憶、主人快照、工作臺、事實卡、提醒、主人 session、T6 owner 參數。
- 可加（待拍板）：主人對這位朋友的偏好（「重要的事要拒絕」等 policy，由 config/relations 提供，不是自由文字）。

**C. 資訊**
- 接收：collector 快照/事件、event_frame、reminders、inbound、Discord 訊息流。
- 三態：collected（原樣）→ usable（正規化：時間/地點/事件/來源/有效期/信心）→ sayable（與主人相關、可回應、可確認、時效內）。
- 入口：①工具查詢（她主動查）②A/D 的事件卡（被動注入，≤300 字）③主動訊息素材（她自己決定要不要說，腳本只給材料）。
- 先 shadow：info_decision 只記錄不注入，兩週後再開。

**D. 群信息**
- 接收：channel 全量訊息（已有落盤）＋結構化：speaker_id/canonical（流螢＝主人小號）、target、reply_author、is_owner、owner_present、addressed_explicit、channel_policy。
- 分流：owner 群 → A 的上下文（背景＋被叫句＋誰在說話）；guest 群 → B 的上下文（channel_context）。
- 群裡預設沉默，只有被叫（@/叫名/回覆她）才回；主動關心另案（主人說分管線、他有私心）。
- 先 shadow：`runtime/shadow/group_parse.jsonl` 兩週，不改行為。

### 8.2 共用層（不變）
人格核心（她是誰）、模型入口/優先級、記憶治理（寫入/召回/證據）、安全與隱私、輸出渲染/繁中、審計/trace、T6 能量（只影響 A；B/D 用態度向量）。

## 9. 待主人拍板的問題

1. 四管道的「輸出權」：A 主動訊息無上限（已定），D 群主動關心是另案，C 資訊的 sayable 要不要給她自己決定？（建議先 shadow 兩週）
2. B 朋友線要不要看「主人對這位朋友的關係卡」？看到什麼程度（只 policy，還是含最近互動摘要）？
