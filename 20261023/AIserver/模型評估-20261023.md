# 模型評估 2026-10-23：ASTRA（規劃）、Cloude（Claude-4.5-Opus distill）、Qwen14b

> 背景：主人問「ASTRA 對長任務和驗收能不能勝任」、以及 Ollama 清單裡的 Cloude（`Qwen3-14B-Claude-4.5-Opus-High-Reasoning-Distill-Q6_K`，12.1GB）拿來做 code、chat 效果如何。
> 測試環境：aiserver 10.0.0.2，RTX 5060 Ti 16GB，Ollama 單 GPU；數據存 `logs/tests/model-compare-20261023-2310.json`、`…-2315.json`。

## 一、ASTRA（`ASTRA-14B-Thinking-v1` Q5_K_M）能勝任長任務嗎？

### 實測（2026-10-23 22:51–23:00，真實自動建任務）
任務：`20261023-待办事项Web应用`（5 步，work→ASTRA plan→task_runner）

| 步驟 | ASTRA 規劃耗時 | 結果 |
|---|---|---|
| 1 | 102.9s → 驗收失敗重試 135.8s | write_file 聲稱成功但檔案不存在（實際是驗收路徑 bug，見下） |
| 2 | 18.5s | 成功 |
| 3 | 299.5s | **未生成任何 tool call** → 任務中止（失敗歸檔 + 通知） |

### 判斷
- **規劃結構可用**：plan 能拆出合理階段（架構→功能→部署），短句協議（task/plan/step/call）基本能遵守。
- **不穩定**：同一模型不同步耗時 18.5s～299.5s；思考鏈很長，容易撞 timeout 或吃光 output 預算後空手而回（step3）。
- **效能瓶頸**：ASTRA 以 32K ctx 載入（16.1GB，15.1GB 在 VRAM、~1GB 掉 CPU）→ prompt eval 慢；step 越後面 journal 越長（step2 的 read_file 摘要 2328 字進 journal）→ step3 prompt 暴增。
- **驗收它自己靠不住**：step1 聲稱寫入成功，實際檔案不在（其中一部分是我們的驗收路徑 bug，但 ASTRA 本身也沒有自檢）。→ 外部客觀驗收（`_verify_step_artifacts`）是必要的，不能省。

### 建議（可討論）
1. **ASTRA 改用 12K 別名**：已建 `astra-12k`（num_ctx 12288，期望 100% GPU、prompt 更快）。基準與原 32K 版本 21.1s vs 21.0s（此輪都吃在 thinking，非結論），需再用真實 step prompt 對比。
2. **journal 摘要化**：每步只留 3–5 行結論，不要把工具長輸出塞進下一步 prompt。
3. **step 規劃 max_tokens 收窄**（8192 → 2048–4096），避免 thinking 吃光額度後空手。
4. **失敗策略**：已補「無 tool call 先重試一次」，仍失敗才中止；驗收路徑 bug 已修（相對路徑基準 `/data/ai/workspace`）。
5. 終極方案：規劃也換 Cloude 試（待追加測試結果）。

## 二、Cloude（`Qwen3-14B-Claude-4.5-Opus-High-Reasoning-Distill-Q6_K`）

### 實測
| 項目 | 耗時 | 輸出 |
|---|---|---|
| chat「我今晚有点累，陪我聊两句吧」 | 17.0s | 去思考後：「知道你累。要休息，还是需要倒杯水？」 |
| chat「你觉得我今天做得怎么样？」 | 7.8s | 去思考後：「尚可。决策时有犹豫，情绪外露了些。若能更果断、更内敛，会更接近你的目标。」 |
| code「is_palindrome + 兩個測試」 | 20.3s | 完整正確程式碼（含 docstring、兩個 assert） |
| 對照 Qwen14b chat 同一句 | 10.6s | 「嗯，你先坐。」 |
| 追加：情緒對話（繁體/去思考）「我今天被同事氣到了，不想說話。」 | 7.0s | 「「嗯。」「在哪？」「我過來。」」 |
| 追加：工程規劃（3 階段 plan） | 27.9s | 乾淨 `<plan>`，格式正確、內容合理（thinking 363 字獨立出） |

> 追加測試（`logs/tests/model-compare-20261023-2315.json`）顯示 Cloude 在**繁體短句情緒對話**上的人味明顯強於 Qwen14b（例：「我過來。」這種帶行動的關心），且規劃輸出乾淨、無思考泄漏；但規劃耗時 27.9s（ASTRA 21s），仍是「好用但不快」。

### 判斷
- **人味確實不差**：回覆有觀察、有分寸，不像模板安慰；語氣偏「內心思考後給結論」。
- **code 可用**：這次單檔函數寫得乾淨完整，比 ASTRA 的寫檔流程直接（但長專案仍需規劃+多步）。
- **問題 1：思考過程會漏進 content**：`content` 裡帶著「用户看起来有些疲惫…」和 `</think>`（模型沒有用 Ollama 的 thinking 欄位），必須在接入前清洗（截到最後一個 `</think>` 之後，或改用 prompt 要求「只輸出最終回覆」）。
- **問題 2：慢**：12.1GB Q6_K，同樣 14B 級但比 qwen14b 慢（17.0s vs 10.6s）；cold load 更慢。
- **問題 3：簡體**：需在 system prompt 明確要求繁體。

### 建議
- **Cloude 有兩個好場景**：①code agent 後端（單檔/多檔實作，輸出乾淨、正確）；②需要人味的繁體短句對話（實測「我過來。」這種帶行動的關心，Qwen14b 做不到）。規劃也能用（27.9s，乾淨 plan），但速度不如 ASTRA，暫不作主力。
- **接入前必做**：response sanitize（思考段漏進 content 時截到最後 `</think>` 之後）＋繁體約束（system prompt 明確要求繁中）。
- **VRAM 策略**：Cloude Q6_K 12.1GB + KV ≈ 13–14GB，可與 3B CPU 共存，但**不能與 Qwen14b/ASTRA 常駐共存**——建議「按需載入」：code 任務前 `ollama load cloude`（或第一次請求觸發），完成後 `keep_alive=0` 卸載、載回 Qwen14b（切換成本約 30–60s，可接受作後台任務）。
- 若要長期雙模型，考慮把 Cloude 量化到 Q4_K_M（約 9GB）或等更大顯存。

### 4.3 接入修正（已落地）
- `call_ollama(..., timeout=None)`：可傳獨立超時；code 用 `CODE_AGENT_TIMEOUT=600`（原 120s 會截斷長答案）。
- Cloude 一律 `think=True`：thinking 由 Ollama 分離，content 乾淨；空回覆自動重試一次。
- `model_swap`：Cloude 預載 `num_ctx=16384`（env `CLOUDE_NUM_CTX`）、Qwen 回載 `num_ctx=16384`；切換成本 = 卸載 + 預載（~40s）。
- `code_agent` 無工具調用時，若答案含「執行結果/測試通過」→ 前面標明「以下是預期輸出，我沒有實際執行」。

### 4.4 結論（更新）
1. **Cloude 適合 code agent 後端**（單檔/多檔實作 + 工具規劃），不適合當常駐 chat（需切換、慢）；chat 維持 Qwen。
2. **後台任務 code 引擎可用但有代價**：每步切走 Qwen ~40–60s，期間聊天變慢/不可用。若要 background 跑 code 任務，需加「主人在線/閒置」門控，或接受空窗（待主人決定）。
3. **ASTRA 建議降為備援**：12K ctx + journal 摘要化 + max_tokens 收斂後再測；目前 code 引擎的 `<file>` 協議比 ASTRA 的 inline 三引號穩。
