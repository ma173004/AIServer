# 多入設計：中文對照與完整復述（2026-11-23）

這份文件只有一個目的：把我們這幾輪用的英文／技術詞，全部翻成中文並固定在這裡，避免再出現「工作臺」那種——同一個詞，我以為在說 A，主人以為在說 B，幾步之後就對不上。

## 0. 先說結論

目前真正可做、而且不是「另一版 after」的，只有一件事：

> **把每一條進來的訊息，從「可能被靜默丟掉」改成「一定有歸屬、一定有終態」。**

這件事不生成第二段回覆、不做語義判斷、不猜主人講完沒有。它只改訊息在系統裡的記帳與收尾方式。

至於「被延後到下一輪的訊息怎麼承接」「更正要不要取代前一句」「一批要回一條還是兩條」——那些會生成新內容，接近 after_turn，目前沒有證明可行，先不做。

## 1. 問題定義

主人可能連續發幾句：
- 同一句話的碎片；
- 補充；
- 更正（「不是」「我是說」「改成」）；
- 換題；
- 社交動作（「我愛你」「晚安」）；
- 情緒升級。

AI 只有一份固定的上下文，生成中不能再「聽」。所以多入只能在**輸入端**處理，不能在生成中即時吸收。

但這次查到的根因不是「收集窗太短」，而是：
- 批次狀態用 `audience` 當鍵，不是頻道／會話；
- 任何回合結束時的 `_mi_finish` 會無條件清掉共用批次狀態，可能清到別的回合正在收集的批次；
- 生成中排隊的訊息只記 id 與字數，**沒有保存原文**；
- 因此昨晚 00:45 的四條訊息，三條在系統裡「有 id、有 log、但沒有內文、也沒有回覆」。

| multi-input（多入） | 多入 | 主人在短時間內連續送進多條訊息 | 不是「一次生成多條回覆」 |
| batching | 分批／收集成批 | 把時間接近的幾條訊息放進同一回合 | 不是把所有訊息永久合併 |
| collection window | 收集窗 | 第一批訊息到達後，願意再等多久收後續 | 不是「猜主人講完沒有」 |
| deadline | 截止時間 | 時間到就定案，不再等 | 不是「等到確定完整」 |
| turn | 回合 | 一次從收到輸入到產生回覆的完整流程 | 不是單一訊息 |
| batch | 批次 | 同一回合內一起處理的一組訊息 | 不是資料庫批次 |
| message ledger | 訊息帳本 | 每條訊息的固定紀錄：誰、何時、哪個頻道、原文、被哪回合處理、最後狀態 | 不是聊天摘要，也不是長期記憶 |
| persist-before-ack | 先寫入，再確認 | 先把訊息寫進帳本，才回覆「收到」 | 不是先回主人再補記 |
| single writer | 單一寫入者 | 同一個狀態只能由一個地方改，避免互踩 | 不是只有一個執行緒 |
| owner-scoped finish | 只收尾自己的批次 | 回合結束只結束自己那一批，不能清別人的 | 不是共用一個大籃子 |
| key by channel/session | 用頻道／會話當鍵 | 大號、小號、不同私聊各自分開 | 不是用「主人」這個身份當唯一鍵 |
| terminal state | 終態 | 每條訊息最後只能落在：已回覆／已被取代／已帶到下一輪／失敗 | 不是「有 log 就算處理」 |
| carried | 被帶到下一輪 | 這條訊息這一輪來不及回，下一輪要帶著它 | 不是「已讀不回」 |
| supersede | 取代 | 後句明確推翻前句，前句作廢 | 不是把兩句拼接 |
| correction-aware | 更正感知 | 知道後句可能在修正前句 | 不是用關鍵詞表硬猜 |
| advisory classification | 建議性分類 | 模型只標註「這批像什麼」，不決定收發 | 不是讓模型決定等多久 |
| non-blocking wait | 非阻塞等候 | 等訊息時不能卡住整個頻道 | 不是 sleep 10 秒 |
| idempotency | 冪等 | 同一條訊息重送兩次，只處理一次 | 不是每次都新建一筆 |

| WAL / fsync | 預寫日誌／強制落盤 | 先寫入磁盘再繼續，防斷電／崩潰丟資料 | 不是一般寫檔 |
| provenance | 出處 | 這句話的依據是原文、工具結果，還是推論 | 不是「我記得」 |

## 3. 目前可做的最小方案（只做資料層，不做語義層）

用白話完整復述一次流程：

1. 主人送來一條訊息。
2. 系統先把這條訊息寫進「訊息帳本」：訊息編號、時間、誰說的、哪個頻道／會話、原文、回覆對象（如果有引用）。
3. 寫入成功後，才讓主人端知道「已收到」。
4. 系統用「頻道／會話」當鍵，決定這條訊息屬於哪個回合。
5. 收集窗到了截止時間，就把目前這批訊息定格成一個「快照」。
6. 只有這個快照的擁有者可以把它送去生成；也只有它可以收尾。
7. 回合結束時，只結束自己的快照；如果還有後續訊息，它們留在帳本裡，狀態是「待下一輪」。
8. 每一條訊息最後都必須有終態：已回覆、已被取代、待下一輪、失敗（附原因）。
9. 如果同一條訊息因重試送來兩次，用訊息編號去重，只處理一次。
10. 事後可以對帳：進來的訊息數 = 各終態總數，不能有「有 id、沒內文、沒回覆」的黑洞。

這個方案**沒有**：
- 沒有第二段生成；
- 沒有用模型判斷「講完沒有」；
- 沒有把「我愛你」和「幫我查資料」硬併；
- 沒有改 prompt；
- 沒有承諾回覆變快。

## 4. 不可做／未證明的部分（先不進生產）

### 4.1 先回再改
「完整句先回，下一輪再承接更正」——不可行。

理由是下午五點的實例：主人在對話裡糾正同一個錯誤，花了半個多小時；如果第一次回覆已經把錯的說出口，下一輪再改，等於讓錯誤多活一輪，還要主人再指出一次。這不是「更正」，是二次傷害。

所以：
- 不要為了低延遲而提前承諾；
- 截止時間到之前，寧可等；
- 截止時間到之後，只能用誠實的「我剛才理解錯了／我重新確認」修復，不能假裝沒發生；
- 但這仍然不是解法，解法是「不要那麼早把不完整的東西當成完整」。

### 4.2 被帶到下一輪的訊息（carried）
「carried」不是標一個旗子就算。它必須是狀態機：
`待處理 → 併入下一批 → 已回覆／已被取代／失敗`，而且要有先後順序。
只寫「已 carried」等於「已知遺失，多一行 log」，00:45 會重演。

### 4.3 更正取代（supersede）
「後句取代前句」是規則，不是機制：
- 哪句取代哪句？
- 取代哪個欄位？
- 「不是」開頭不一定是更正；
- 沒有已標註的語料，無法量對錯。
所以先只做 shadow 建議，默認不要把兩句硬併；由 gateway 按引用與時間把兩句都留著，模型不自行判定。

### 4.4 社交動作獨立承接
「我愛你」「晚安」是否一定要獨立一條回覆？目前沒有準則。
預設應該是單回覆吸收，否則主人會收到氣泡轟炸；但要先定「一氣泡吸收全部」或「最多兩氣泡」的規則。

## 5. 為什麼「這好像又是另一版 after」

- after_turn 是：主人回合結束後，再從舊材料生成 thoughts／say／line。
- 我上一版提的「先回、下一輪承接更正」也依賴第二次生成，所以它本質上就是另一版 after_turn。
- 這次可做的「訊息帳本＋擁有者收尾」不是生成，不會多一段話，所以不是 after_turn。
- 如果某個方案需要「下一輪再生成一段來補救」，就應該先當成 after_turn 的變體來審，而不是當成多入修正。

## 6. 驗收與失敗線（資料層）

- 進來訊息數 = 已回覆 + 已取代 + 待下一輪 + 失敗，無黑洞。
- 同一訊息重送只處理一次。
- 任一回合結束，不能清掉別人的批次。
- 大號、小號、不同私聊不互相清批次。
- 每個失敗都有原因，不能靜默。
- 回覆延遲不變差；若變差 >20%，停下檢查。

## 7. 仍待主人決定

1. 一批預設回一條，還是允許 1–2 條？
2. 被延後到下一輪的訊息，當輪要不要先說「我收到你這幾條」？
3. 要不要先只做資料層（訊息帳本＋擁有者收尾），語義層等語料？

這三個問題不回答，後面的「更正感知」「社交動作拆分」「承接」都會變成猜。
